# 插件包更新

设置 → 应用 → 插件包，在要替换的那一版旁点击 **更新…**，选择同一插件 ID、更高版本的 `.rmplugin`。确认页列出旧版、新版、作者声明、受影响仓库与阻止原因。

- **更新**：替换本机已登记仓库对所选旧包的绑定；启用的仍启用，停用的仍停用。全部完成后删除旧包。
- **添加插件**：继续支持多版本并存，由用户到各仓库选择版本；需要保留旧包时使用此入口。
- 只替换选中的旧版本，不把其他已安装版本或各库选择合并为“最新”。不修改插件数据、设置、密钥或工作台安排，不执行卸载清理；新版启动本身仍可能按其声明加工数据。
- 已打开的受影响仓库先按原页面生命周期保存，随后重新加载；未打开的仓库经临时核心检查并仅修改版本绑定，不启动后台加工或界面。正常重新打开时再按新版装配。

## 检查与边界

更新扫描本机包授权／使用登记、最近仓库和打开的仓库；不会遍历磁盘找未登记的副本。已登记路径不可访问时拒绝继续，不把它当作“已经没有引用”。路径移动或外置盘离线需要先处理。

先检查包完整性、ID、版本、宿主能力、持久定义兼容性和依赖装配。已有持久结构不兼容时仍拒绝加载，更新不是绕过结构契约或清空旧数据的入口。核心预检复用正式加载校验，启停配置用原绑定比较后替换，不覆盖并发改变的选择；关闭仓库仍遵守唯一写入锁。

以下情况不会强行替换或删除：

- 正在应用插件选择，或目标插件仍有开发覆盖；先结束相应流程。
- 未完成建库／方案应用任务固定引用旧包摘要，需先接续或取消任务。套件和用户方案中的摘要仅作推荐，不再阻止更新；原版推荐信息不被暗改，应用时可选择已安装版本。
- 仓库还在运行与已保存选择不同的旧版；先重新加载该仓库。
- 某仓库加载新版失败，或旧包仍被引用。

已打开且启用插件的仓库，需要确认核心、界面装配与服务启动成功；尚未打开的仓库做核心及数据兼容检查，不承诺已经验证其界面和全部业务。受信任插件代码不是沙箱，作者声明也不是签名认证。

## 失败和中断

任务与候选包快照保存在本机用户目录的 `plugin-updates/`，应用重启或设置窗口重载后，可回到插件包页继续。开始后不重新读取用户选择的源文件。

| 阶段 | 失败后的状态与处理 |
| --- | --- |
| 预检、尚未替换任何绑定 | 旧选择保持，可重试或取消；已经安装的候选包保留，可按普通插件包卸载。 |
| 已开始替换仓库绑定 | 各库事务独立，部分库可能已更新。继续更新会复核库身份和原选择，并幂等接续。不能声称整批回滚。 |
| 新版本自身故障，暂时无法继续 | 可明确选择“结束更新并保留两版…”。已提交选择保持，旧包和新包都保留，随后可添加修正版或手动调整；不撤销新版已产生的数据变化。 |
| 全部绑定已更新，正在清理旧包 | 继续完成清理，不重复替换；即使旧登记已移除但文件删除中断，也可接续。 |
| 完成 | 旧包及旧授权记录已移除，结果可关闭；随应用附带的旧包登记也转向新版，避免重启重新安装旧版。 |

未完成任务期间，安装／卸载、启停应用和开发覆盖变更会被拦住，避免改变其确认范围；允许查看数据及恢复页面。结束失败任务后恢复正常管理。

这里的成功是“替换与装配完成”，不保证新版业务永远无错误。日后需要旧版时仍可用原包重新添加，但数据若已演变，降级依旧要通过兼容检查。

## 实现归属

- `src/plugin-packages/updates.ts`：持久任务、候选快照、阶段与幂等接续。
- `src/main/plugin-updates.ts`：本机引用核对、仓库进程协调、页面收尾和运行结果确认。
- `src/core/package-update.ts`：在对应仓库的唯一核心里预检和比较后替换。
- `PluginUpdater`：预览、确认、继续和结果反馈；使用应用 IPC，不要求业务插件实现更新代码。

包格式和仓库格式不变，不增加插件公开 RPC 或 MCP 写操作。验证入口见[开发与验证](../development/开发与验证.md#插件包替换更新)。
