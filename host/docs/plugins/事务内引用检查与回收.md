# 事务内引用检查与回收

实现日期：2026-10-20。用于 Collection、歌单、项目等“当前素材引用其他实体”的业务。框架提供检查和生命周期能力，目标是否合法、允许哪些成员、怎样处理冲突仍归插件。完整独立示例见 [transaction-plugin](../../examples/transaction-plugin/core.ts)，它是接口验证示例，不是正式 Collection 插件。

## 导入时读取引用目标

`IngestMetadataContext.readEntity(id, kinds)` 在导入提交事务中读取同一仓库的最新数据：

```ts
const target = ctx.readEntity(input.group as string, ['my-plugin.group'])
if (!target || target.deleted || !target.blocks['my-plugin.group']) {
  throw new Error('目标不是有效的组')
}
ctx.put('my-plugin.member', { group: target.id })
return { status: 'applied' }
```

- 不存在返回 `null`；存在则返回 `{ id, deleted, blocks }`，回收站实体仍可读取，`deleted: true`。停用插件留下的块也可读，业务处理器决定是否接受。
- `kinds` 必须显式传入，最多 20 项；只返回选中的现存块。传 `[]` 只检查存在和删除状态，不加载正文等其他块。
- 返回独立副本，修改结果不会写回仓库。当前素材的 `blocksOf()` 不变；`put` 仍只能修改当前素材上本插件允许的持久块，没有获得其他实体的写权限。
- 每个附加处理器最多 100 次读取；一次结果最多 1 MiB，累计最多 4 MiB（序列化 UTF-8 字节数）。超限抛出 `INGEST_READ_LIMIT`，由导入管线包装为 `INGEST_METADATA_FAILED` 并回滚本次提交。输入 ID 与 kind 长度限 1～200 字符。
- 生命周期与附加处理器相同，返回或抛错后不可保留上下文继续读取。它不是全库扫描接口，不提供搜索、SQL 或跨库访问。

输入 schema 在复制前校验，但目标存在／删除状态必须在 `apply` 中检查。复制过程中用户可能删除组；提交时检查和关系写入同步处于同一事务，检查失败则整批准备成功的文件与附加修改一起回滚。它不会锁住整个文件复制过程，也不会缓存复制前的目标状态。

外部包应同时声明 `coreFeatures: ["ingest-metadata-v1", "ingest-read-v1"]`。后者是新宿主能力标记，旧宿主拒绝未知特性；它不替代业务检查。宿主校验 `ingest-read-v1` 必须同时有导入协议声明。

## 作品拥有的从属记录

外部包可声明 `owned-records-v1`，给作品的摆放、歌单条目等各自分配稳定 ID。块定义使用 `standalone: true`、`rebuildable: false`、`ownedBy: 'owner'`。其中 `owner` 必须是唯一的单值 `ref: 'attach'` 字段，指向活跃内容素材。引用的图片、曲目等来源可另用 `ref: 'link'`。

所属插件在同一条命令里用 `ctx.createEntity()` 和 `ctx.put()` 创建记录。每个从属身份只承载这一种块，并保留撤销历史。插件列出作品成员时使用 `scope: 'all'`、指定 `has`，再以已索引的归属字段筛选。默认素材浏览及回收站只展示作品。

- 回收、恢复或彻底删除作品会处理它的从属记录。停用插件后，宿主继续使用库内保存的定义执行这些操作。
- 从作品移除单个成员，调用所属插件的 `ctx.deleteRecord(id)`。撤销能恢复同一 ID 与字段。来源素材的生命周期独立。
- 彻底删除作品后，可能把已移除成员恢复到该作品的旧操作一并失效。

## 多个持久块的条件提交

外部插件声明 `coreFeatures: ["command-preconditions-v1"]`。开始交互时逐项记下 `blocks[kind].seq`，在同步命令中传给 `ctx.expectBlocks([{ id, kind, seq }, …])`，再写入新值。一条命令可核对 1～1000 个条件。块被改写、移除或实体已回收时抛出 `[BLOCK_CHANGED]`，本次命令内的修改一起回滚。插件在提示冲突后重新读取，让用户决定是否再次操作。MCP 可用 `read_items` 读取同一序号，然后通过插件的 operation 提交。

如果页面编辑从属记录，同时希望检查器展示来源素材，可声明 `uiFeatures: ["page-delete-v1"]`，在标签类型设置 `deleteTarget: 'page'`。用 `setFocus(sourceIds)` 选择检查对象，用 `expose({ pageSelection: { ids: memberIds, remove } })` 报告页面选择并处理删除。原生删除菜单和键盘删除均使用页面选择。选区为空或组件暂时卸载时，宿主仍保留这项路由。工作台会话对这种页面分别返回 `target.selectedIds` 和 `target.inspectionIds`。

## 命令内移入回收站

`CommandContext.trash(ids)` 给同步业务命令提供回收站操作：

```ts
trashGroup(ctx, args) {
  const id = args.id as string // 入口先用 schema 校验
  if (!ctx.query({ ids: [id], has: ['my-plugin.group'] }).ids.length) {
    throw new Error('组不存在或已删除')
  }
  ctx.trash([id])
  return { label: '删除组', result: { id } }
}
```

插件决定业务准入；框架统一执行以下规则：

| 情况 | 结果 |
| --- | --- |
| 输入 | 1～100 个非空 ID，每个最多 200 字符；重复 ID 去重 |
| 任一显式目标不存在 | 抛出 `NOT_FOUND`，整个命令回滚 |
| 显式目标或依附链含管理记录 | 拒绝，管理记录仍走所属插件的 `deleteRecord` |
| `attach` 依附内容 | 沿既有生命周期随目标回收，一起撤销恢复 |
| `link` 关联内容 | 不回收、不清理引用；“删除组后视为未分组”等解释由插件负责 |
| 已在回收站 | 不重复改变删除时间；没有变化时不新建撤销步骤 |
| 原文件 | 保留库内原文件，不移动到系统废纸篓 |

它加入当前命令的事务与一次撤销，命令后续抛错会连同其他数据修改一起回滚。`api.preview` 可以预演，预演结束后数据恢复。后台任务根据事务结束后的删除状态取消，包括依附内容；预演或失败回滚不会因为短暂写入了删除状态而取消活跃素材的加工。

所有命令经同一同步调用边界执行，UI `run`、`preview` 和 MCP operations 一致。命令返回／抛错后上下文失效，保留回调再调用会报 `COMMAND_CONTEXT_EXPIRED`；返回 Promise 的实现报 `INVALID_COMMAND`，同步部分随事务回滚，异步续写不能继续使用上下文。旧命令本来就要求同步，这次增加运行时检查。

外部包使用这项能力时在 `coreFeatures` 加入 `command-trash-v1`，确保旧宿主拒绝不兼容包。这是可信插件 API 和兼容声明，不是恶意代码隔离机制。命令仍未开放彻底删除和清空回收站。恢复能力见下节。

## 命令内恢复

`CommandContext.restore(ids)` 与 trash 对称：1～100 个普通素材 ID、先整体校验存在及素材角色、去重后恢复。不存在或已彻底删除时报 NOT_FOUND，管理记录拒绝；活跃素材重复恢复不增加撤销步骤。沿用 Store 的恢复规则：和父项同批进入回收站的 attach 依附者恢复，先前单独删除的依附者保持删除，link 目标不随行。

该调用仍在当前同步命令的事务中，可预演、整体回滚、撤销／重做，返回后上下文失效。恢复后的加工沿用正常数据变更与调度流程。外部包声明 `command-restore-v1`，旧宿主拒绝该包，须先更新应用；不需要依赖 MCP 插件。

业务插件自行核对对象类型并声明 operation，例如 Collection 的 `collection_restore` 校验组，再调用 ctx.restore。MCP organize 权限、requestId 回执和重试规则沿用现有入口；read 模式不能恢复。插件可以用 `ctx.query({scope:'trash',has:['自己的块'],ids:[id]})` 校验回收站对象。通用 MCP 同样已有 search_items 的 trash 范围，查询回收站不能替代恢复动作。

## 与 MCP 和 Collection 的关系

MCP 没有新增一个任意删除工具。插件明确发布自己的 operation，例如 `collection_delete → trashGroup`；仍经 `execute_operation` 调用，沿用仓库 `organize` 权限、输入校验、请求签名、回执和一次撤销。操作名称当前使用小写字母／数字／下划线，不是带点号的查询命名。

成功删除后即使用户撤销，重复的 `requestId` 只返回原回执，不再次删除；重启同样如此。检查当前状态使用读取工具。尚未成功提交的导入失败没有成功回执，目标恢复后可以用原 ID 与原参数重试。

Collection 可以据此实现：先创建组，再用 `collection.join` 在收录时检查组并写成员 link；删除组通过命令回收。建组和后续导入仍是两个独立事务，不保证跨请求整体原子性。空组保留、有效未分组查询、成员顺序和封面规则都由 [Collection 插件](../README.md)实现；宿主与 MCP 不加入 Collection 特例。
