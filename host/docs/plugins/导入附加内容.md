# 导入附加内容：一次收录与多个插件协作

核对日期：2026-10-19。公共契约是 [ingest.ts](../../src/plugin-api/ingest.ts)，外部包从 `@resource-manager/plugin-api/ingest` 导入。首批实现见 [tags](../README.md)、[note](../README.md)、[source](../README.md)。

## 目标与职责

调用者在收录文件时表达“追加这些标签、补充这段笔记、记下来源”。插件声明可接受的业务意图、输入 schema 和已有数据的处理策略；宿主负责发现、校验、去重后的身份、事务、撤销与回执。MCP 转发公共协议，不包含标签或笔记的业务分支。

这里的 `metadata` 是按能力 ID 组织的输入，不是任意数据块写接口。数据块仍由所属插件解释和写入；调用者不能靠猜测块名改文件路径、管理记录或派生内容。

## AI 怎样调用

先 `list_libraries`，必要时打开目标库，再调用 `describe_library`。它的 `ingestMetadata` 列出当前启用插件提供的 `id / title / description / inputSchema`。同时查看 `operations` 中 `import_files` 的 schema。

调用 `execute_operation`，每个文件可以携带不同内容：

```json
{
  "libraryId": "目标仓库ID",
  "operation": "import_files",
  "requestId": "import-with-metadata-001",
  "args": {
    "files": [{
      "path": "/absolute/path/image.png",
      "metadata": {
        "tags.add": { "add": ["阅读", "参考"] },
        "note.initial": { "text": "这份资料讨论了插件间的协作。" },
        "source.initial": { "url": "https://example.com/article", "title": "原文" }
      }
    }]
  }
}
```

旧的 `args: { paths: [...] }` 完全保留；`paths` 与 `files` 必须且只能给一个。每次最多 20 个本机普通文件，不支持目录、通配符或直接抓取 URL。每项最多 20 种附加能力，附加内容序列化后最多 128000 字符；各能力还会施加自己的限制。

首次使用需要更新宿主，并在当前仓库选择标签 **1.5.0**、笔记 **1.1.0**、来源 **1.1.0** 中需要的插件，再统一应用重载。已有仓库绑定不会自动换新版；没有启用的能力不出现在描述里。调用前重新获取描述，不能只凭源码或已安装包判断可用性。

| 能力 | 输入 | 去重命中已有素材时 |
| --- | --- | --- |
| `tags.add` | `add`：1～20 个非空标签，每个最多 100 字符，去掉首尾空白 | 去重追加并保留其他标签；不改变标签分组 |
| `tags.set` | `values`：0～100 个非空标签，每个最多 100 字符，去掉首尾空白 | 整体替换标签（含已有素材），空数组清空；不改变标签分组 |
| `note.initial` | `text`：非空白文本，最多 32000 字符 | 没有笔记或笔记为空白时填入；已有不同笔记保留。Markdown 缩进和换行原样保存 |
| `source.initial` | HTTP/HTTPS `url`，最多 2048 字符；可选 `title` 最多 200 字符 | 仅缺少来源网址时补充；已有来源不覆盖，包括同 URL 的标题差异 |


`tags.add` 与 `tags.set` 写入同一个标签块，一次导入只能使用其中一个；同时给出会整次失败，不产生回执。

结果沿用 `items / errors / processing`。`items[].outcome` 仍为 `created / existing / restored`，有附加意图时另返回 `items[].metadata`：

```json
{
  "tags.add": { "status": "applied" },
  "note.initial": { "status": "preserved", "message": "已保留原有笔记；新笔记未写入" }
}
```

`applied` 表示已应用，`unchanged` 表示不需要改变，`preserved` 表示按照插件规则保留了旧值。调用者必须检查结果，不能把 `preserved` 当作新值写入成功。需要覆盖笔记时，另行读取当前版本，再调用 `set_note` 并传 `expectedSeq`。

## 事务、重试与读取

1. 所有项的附加能力和参数在文件复制前校验。未知／停用能力返回 `UNAVAILABLE_INGEST_METADATA`；能力参数错误返回 `INVALID_INGEST_METADATA`，通用输入形状错误返回 `INVALID_INPUT`。整次拒绝，不产生收录或回执。
2. 普通文件错误仍逐项报告，例如第三个路径不存在，前两个可以成功；`index` 对应输入项，从 0 开始。成功项的收录、附加写入和请求回执同事务提交，形成一次撤销。
3. 处理器执行错误包含 `INGEST_METADATA_FAILED`，本次仓库收录和已有素材修改一起回滚，不生成成功回执。2026-10-26 起文件先独立保存到默认文件空间；若新文件已保存，外层报 `FILE_STORED_NOT_ADOPTED` 并保留原失败原因、字节及仓库收录草稿，不删除空间文件。修正原因后用原请求 ID 和原参数重试，重启后也可复用已保存内容；没有启动自动重试或未收录文件清理界面。
4. 附加处理在提交阶段读取最新数据。准备文件期间用户编辑了笔记，`note.initial` 会保留最新笔记。同批重复文件按输入顺序作用于同一身份，后一项读取前一项的结果；回收站去重命中仍会恢复素材，恢复和附加内容一起撤销。
5. 成功请求超时重试用同一 `requestId` 与原参数，重放回执，不再次写入。撤销后重试也不恢复素材；回执反映原操作，当前状态请重新读取。部分文件失败已有回执，修正失败项后要用新 ID 重试这些项。
6. 导入仍返回 `processing: "not_waited"`。附加内容已提交，但 PDF 正文、封面等后台加工可能未完成；随后使用 `read_item` 查看加工状态、`read_content` 读取内容。业务解释可继续使用 `execute_query`，后续修改使用 `execute_operation`。

MCP 写入沿用仓库的 `organize` 权限；只读模式仍可发现和读取，但不能通过附加内容写入。停用插件撤下它的导入能力，已有数据保持通用可读。已有成功回执仍可重放，不能据此推断插件当前启用状态。

## 插件怎样接入

在自己的 `plugin.json` 声明 core 入口，并把 `ingest-metadata-v1` 加入 `coreFeatures`（保留已有特性）。较旧宿主会拒绝未知特性，需先更新宿主；不能省略特性声明绕过兼容检查。再在 `CorePlugin.ingestMetadata` 注册声明。ID 以自己的插件 ID 加 `.` 开头，在本插件内唯一，schema 必须描述对象。

以下示例假设 `my-plugin.info` 是本插件已声明的普通持久数据块，含 `text` 字段：

```ts
import { z } from 'zod'
import type { IngestMetadataDefinition } from '@resource-manager/plugin-api/ingest'

export const ingestMetadata: IngestMetadataDefinition[] = [{
  id: 'my-plugin.initial',
  title: '导入时补充说明',
  description: '只在说明为空时补充，已有不同说明保留。',
  input: z.object({ text: z.string().min(1).max(2000) }).strict(),
  apply(ctx, input) {
    const current = ctx.blocksOf()['my-plugin.info']?.data
    const text = input.text as string // 已由声明的 schema 校验
    if (current?.text === text) return { status: 'unchanged' }
    if (current?.text) return { status: 'preserved', message: '已保留原说明' }
    ctx.put('my-plugin.info', { ...current, text })
    return { status: 'applied' }
  }
}]
// core.ts 中：export const plugin: CorePlugin = { ..., ingestMetadata }
```

上下文提供当前素材的 `id`、`outcome`、`blocksOf()` 和 `put(kind, data)`；2026-10-20 新增 `readEntity(id, kinds)`，用于在提交事务内有界只读检查其他实体，详见[事务内引用检查与回收](事务内引用检查与回收.md)。读取返回当前块的独立副本；`put` 自动绑定当前身份，只允许本插件启用的普通持久块，不开放派生块、管理记录、standalone 记录、不留历史的块或含文件字段的块。字段仍通过仓库定义校验。不能新建身份、删除其他记录或直接写另一个插件的块。

处理器必须同步返回有效状态，可选消息最多 1000 字符；上下文在返回或抛错后失效，保留回调不能延迟写入。不要联网、发起后台任务或产生不可回滚的外部副作用。较慢的识别、AI 生成应在调用前完成，或使用独立后台加工。

各能力按 ID 排序执行，但不要依赖其他能力的执行顺序。一个素材的一轮附加处理中，同一个块只能写一次；多个能力写同一块会整次失败，应由插件合并为一个业务意图。核心只校验结构和写入边界，业务上的合并、冲突、重复判断以及返回状态由插件负责。这仍是可信插件协作协议，不是恶意代码沙箱。

## 与既有入口的关系及当前范围

- `afterIngest` 保留，仍先于显式附加处理执行。它适合从既有输入自动补全；显式意图用 `ingestMetadata`，调用者才能发现参数与结果。来源插件在存在 `source.initial` 时跳过旧 `input.source` 提示，显式输入优先。
- 底层公共 `api.ingest` 的 file、text、bytes 输入均可携带 `metadata`；bytes 转换和 UI 文件夹展开会保留它。UI 入口仍返回 ID 数组，不返回逐能力报告；需要完整状态的自动化走 `execute_operation`。本轮没有新增手工导入表单。
- `create_text` 继续使用原来的 `content / tags / source` 参数，没有在本轮改成通用附加协议。它的后续统一需单独确认兼容方案。
- 本轮只提供标签、笔记、来源三个业务实现；歌单、模板字段等不会因为能写数据块就自动支持。后续插件按此声明自己的业务入口，无需新增宿主或 MCP 分支。跨身份修改、联网抓取、异步处理链及任意操作编排不在本轮范围。
