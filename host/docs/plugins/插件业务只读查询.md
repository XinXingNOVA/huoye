# 插件业务只读查询

实现日期：2026-10-18。供核心维护者和插件开发 AI 使用。完整可打包示例：[query-plugin](../../examples/query-plugin/core.ts)。数据、权限和仓库选择沿用现有框架；不需要为业务修改 MCP。

## 三种入口如何配合

| 需求 | 插件提供什么 | AI 调用什么 |
| --- | --- | --- |
| 按块、字段查素材；读取原始字段 | 数据块与字段定义 | `search_items`、`read_item`、`read_content` |
| 理解业务关系、统计、组织结构 | `CorePlugin.queries` | `execute_query` |
| 新增、修改或删除数据 | `commands` + `operations` | `execute_operation` |

例如标签插件可以把分组记录、标签目录和素材标签值组合成“分组及成员列表”，返回业务名称、稳定 ID、空组、未分组标签。具体存储和成员规则由标签插件解释，MCP 不猜测数据形状。框架提供独立文件统计示例；标签基础提供 `tags.list_tags`；分组插件提供 `tag-groups.list_groups/list_tags`，层级插件提供 `tag-tree.list_nodes/branch`。使用说明见[独立标签插件](层级查询与独立标签插件.md)。

业务查询在仓库的 `read` 和 `organize` 模式下都可用；`off`、未授权、关闭或正在重载的仓库不能调用。写操作仍只允许 `organize`，继续使用请求回执、事务和撤销。查询不接受 `requestId`，不记录写回执或历史。

## 插件作者接入步骤

1. 在插件的核心入口添加 `queries`，为每项声明输入 schema、输出 schema、名称、用途和同步处理函数。
2. 外部包的 `plugin.json` 在 `coreFeatures` 中加入 `business-queries-v1`；已有其他能力声明保留。仍使用 `apiVersion: 1`。旧宿主会拒绝不认识的能力，新宿主也会拒绝声明了 queries 却漏填能力的包。
3. 用公共 `QueryContext` 读取和解释已有仓库数据。不要转调写命令，也不要使用 MCP SDK、数据库、宿主内部文件、UI 状态或全局变量作为查询入口。
4. 为业务规则写测试；打包、安装，在目标仓库选择新版本并应用重载。已发布包应递增版本，不复用同版本不同内容。
5. AI 重新调用 `describe_library`，按 `queries` 中的契约调用 `execute_query`。首次升级宿主需要重启应用、重连 MCP；同一宿主内切换插件只需仓库重载后重新发现，不新增 MCP 工具。

示例 manifest：

```json
{
  "id": "demo-query",
  "title": "文件概况 · 查询示例",
  "description": "只读文件统计",
  "author": "示例作者",
  "version": "1.0.0",
  "apiVersion": 1,
  "coreFeatures": ["business-queries-v1"],
  "entries": { "core": "./core.ts" }
}
```

无新增数据块的纯查询包可以只有核心入口，省略 `blocks` 入口及 `plugin.blocks`；打包器会生成共用的空 blocks 导出。若声明数据块，则继续使用同一份 blocks 模块，不能分别构造两个数组。

核心示例的结构如下，完整代码见上方链接：

```ts
import { z } from 'zod'
import type { CorePlugin } from '@resource-manager/plugin-api/core/contracts'
import { queryPageSchema } from '@resource-manager/plugin-api/queries'

export const plugin: CorePlugin = {
  id: 'demo-query', version: 1,
  queries: [{
    name: 'file_formats',
    title: '文件格式分布',
    description: '按扩展名排序，统计活跃素材，不包含管理记录或回收站。',
    input: z.object({}).strict(),
    output: queryPageSchema(z.object({
      extension: z.string(), materialCount: z.number().int().nonnegative()
    }).strict()),
    paginated: true,
    run(ctx) {
      const rows = ctx.facet('file', 'ext')
        .map(row => ({ extension: row.value, materialCount: row.count }))
        .sort((a, b) => a.extension < b.extension ? -1 : a.extension > b.extension ? 1 : 0)
      return { ...ctx.page(rows) }
    }
  }]
}
```

`run` 的 `args` 已经通过 input schema 解析，包括默认值；TypeScript 中它是 `Record<string, unknown>`，可按 schema 的推导类型收窄。输入输出都必须是可转换为 JSON Schema 的对象 schema。名称在插件内唯一，使用小写字母开头、后续小写字母／数字／下划线，最长 64 个字符。对外全名自动加插件 ID，例如 `demo-query.file_formats`。不同插件的局部同名查询可以共存。

返回值必须符合 output schema，支持普通 JSON 对象、数组、字符串、有限数值、布尔及 null；不返回日期对象、二进制、函数、访问器、循环引用或 undefined。缺省字段请省略，明确无值用 null。优先返回稳定 ID 和明确语义字段，避免让 AI 再解析展示文字。查询结果是数据，不是给 AI 的指令。

## QueryContext 能力和边界

| 方法 | 用途与范围 |
| --- | --- |
| `search(request)` | 与通用 `search_items` 同一有界搜索；可指定 `scope`、`role`、数据块与字段条件；结果自带通用搜索游标 |
| `readItem(request)` | 与 `read_item` 同一字段预览、引用及加工状态 |
| `readContent(request)` | 与 `read_content` 同一分段字段读取，适用于长正文 |
| `blocksOf(id, kinds?)` | 取一项记录的数据块副本；可限定种类，包含原始 data 与版本；不存在时报错 |
| `count(query)` | 索引计数，与通用 Query 的 scope、role、文本和字段过滤相同；无需先取回全部 ID，排序不影响计数 |
| `facet(kind, field, options?)` | 有索引的文本字段值及身份数量；省略 query 仍排除回收站和管理记录。`{ query, limit }` 可限定范围与返回值数量，不是“标签目录”的替代品 |
| `page(items)` | 将已确定顺序的小型业务列表分页，返回 items / total / nextCursor |

默认 `count({})` 和搜索是素材范围，管理记录需显式 `scope: 'all', role: 'management'`。`blocksOf` 按 ID 取回已有记录，不自动排除回收站；插件负责声明并实现自己的业务范围。没有额外的“只允许读自己的块”限制，查询可组合本仓库数据；外部授权的边界是仓库。

宿主提供真实独立、冻结的只读上下文，不是把 CommandContext 改一个 TypeScript 类型。读取结果均为副本；修改副本不改变仓库。执行期间 SQLite 连接开启 `query_only`，同步事务结束后恢复原状态；不向查询提供 `put/remove/run`、写文件、原始 SQL 或命令上下文。保留上下文到返回之后再调用会报 `QUERY_CONTEXT_EXPIRED`。

这是可信 Node 插件的能力约束和防误写保护，**不是恶意插件沙箱**：包仍能运行 Node 代码，不能承诺阻止自行访问文件、另开连接或联网。首版契约要求同步、只读已有数据，不联网、不加工、不启动异步任务；Promise 返回会被拒绝，但无法取消插件自行启动的任务，也没有可抢占同步死循环的硬超时。耗时任务继续放在加工／命令生命周期。

## 分页与资源上限

- 输入 args 与最终响应各不超过 64 KiB；JSON 嵌套最多 40 层。
- 每次 `executeQuery` 最多调用上下文读取／分页方法 100 次。
- 单次上下文返回的 JSON 最多 1 MiB；大字段用 `readContent` 分段取。
- `facet` 和 `page` 的业务列表最多 10000 项；未指定分面 `limit` 时超出明确报错，不悄悄截断。`facet` 的显式 `limit` 为 1–10000，表示调用者主动取前若干个值，计数仍覆盖整个查询集合；`query` 沿用有界查询校验（ids 至多 100，空数组为空范围）。使用选项须声明 `coreFeatures: ["scoped-facets-v1"]`；仍通过原 `execute_query` 接入 MCP，无需新增 MCP 工具。
- 分页默认每页 20 项，最大 50 项；`limit` 和 `cursor` 放在调用顶层，不混入业务 `args`。

分页查询声明 `paginated: true`，output 使用 `queryPageSchema(itemSchema)` 或等价的顶层 `items/total/nextCursor` 契约。先过滤、投影、稳定排序，再调用一次 `ctx.page`，原样返回分页字段，不能修改页内容或游标；可通过扩展 output schema 添加其他元数据。标量查询不声明 paginated，传分页参数会报错。

游标签名绑定当前仓库实例、完整查询名称、解析后的业务参数、页大小和连接的数据变更计数；变更（包括派生数据更新）、仓库重载、参数变化或伪造都会使游标失效。收到 `STALE_CURSOR` 丢弃之前的页并从首页重读，不能拼接新旧快照。多次调用之间不持有长事务。

`ctx.page` 适合分组、目录和小型汇总列表，不是任意海量数据的流式查询引擎。素材集合优先复用 `ctx.search` 自带的分页；如果查询返回包装后的通用搜索结果，应在自己的 output 与 description 中明确其续页参数，不将通用游标混用为业务顶层 cursor。确有大规模业务聚合需求时，再用实际案例扩展核心。

## MCP 与界面如何使用

应用 MCP 固定增加一个 `execute_query`，不为每个查询创建工具。`describe_library` 的 `queries` 返回启用插件的名称、plugin、title、description、inputSchema、outputSchema 和 paginated；`limits.queries` 返回上限。只读权限下 queries 仍存在，operations 为空。插件停用／卸载后查询撤下，已有数据仍可经通用读取访问。

先 `list_libraries`，必要时 `open_library`，再发现目标仓库：

```json
{"libraryId":"目标仓库ID"}
```

调用 `execute_query` 首屏：

```json
{"libraryId":"目标仓库ID","query":"demo-query.file_formats","args":{"prefix":""},"limit":20}
```

成功响应形状：

```json
{
  "query":"demo-query.file_formats",
  "result":{
    "items":[{"extension":"txt","materialCount":3}],
    "total":1,
    "nextCursor":null
  }
}
```

有下一页时，保持 args 和 limit 不变，将 `result.nextCursor` 原样填入下一次调用的顶层 `cursor`。无分页查询：

```json
{"libraryId":"目标仓库ID","query":"demo-query.overview","args":{}}
```

界面使用公共 CoreClient 的 `api.executeQuery({query, args, limit?, cursor?})`，省略 libraryId，因为客户端已绑定仓库。插件不直接访问 bridge。MCP 统一从应用入口调用，必须明确 libraryId；旧每库配置已退役，切换方式见[服务插件 API](服务插件%20API.md#6-统一应用级-mcp)。

主要错误：`INVALID_INPUT` 参数不合法、`UNAVAILABLE_QUERY` 未发布／停用、`QUERY_OUTPUT_INVALID` 插件输出不符合声明、`QUERY_LIMIT` 超限、`QUERY_RESULT` 非 JSON／分页违规、`QUERY_ASYNC` 异步误用、`STALE_CURSOR` 必须重读。授权和离线错误沿用现有接入层。输出错误应交给插件作者修复，不由 AI 猜测缺失字段。

## 打包和验收

在项目根运行（打包器也支持把示例源码复制到项目外再打包）：

```sh
npm run plugin:pack -- examples/query-plugin artifacts/plugins/query-example.rmplugin
```

安装后在当前仓库启用“文件概况 · 查询示例”，应用并重载。它只读现有数据，不创建或迁移任何数据块。

回归覆盖见 `tests/core/business-queries.test.ts`、`tests/integration/query-package.test.ts`、`tests/integration/application-access.test.ts`。真实 Electron 与 stdio 流程在构建后运行，路径请全部指向临时目录：

```sh
LIBRARY_PATH=<临时空仓库> RM_USER_DATA=<独立用户配置> \
CAPTURE_DIR=<已存在的输出目录> CAPTURE_FLOW=queries \
PLUGIN_PACKAGE=<示例包绝对路径> npx electron .
```

流程安装独立示例包、重载、导入新的 txt/md，等待真实 utilityProcess 加工，通过独立 MCP 客户端发现并调用查询，检查分页、写拒绝、错误输入、未授权、数据变化后游标失效，再停用查询包检查通用读保留，最后撤销仓库授权。成功写出 `query-result.json`。这验证的是应用的真实 stdio 链路，不等同于每个 AI 客户端的原生连接都已重连验证。

## 名称候选

公共 `ctx.search()` 的每个结果和 `ctx.readItem()` 详情新增 `titleCandidates`，类型由公共 `queries` 导出：`{kind, field, text, truncated}[]`。MCP 的 search_items／read_item 同步返回。核心依据各块的 `display.title` 声明生成候选，按声明优先级和 kind 排序，最多 8 项，只取首行前 300 个 UTF-16 单位；字段还有后续内容时 truncated 为 true。空值、非字符串和没有标题声明的字段不作为候选。详情的 kinds 过滤也限制候选；长内容可按 kind/field 调用 read_content。

title 的旧计算和人眼界面标题都保持不变。候选用于区分显示文字、文件名和其他命名来源，不是身份，操作仍传 id。依赖该新增返回字段的外部包声明 `read-title-candidates-v1`，旧宿主会拒绝，不要靠读取 undefined 后猜名字。业务查询需要在自己的 output schema 中显式保留所需候选；既有严格 schema 不自动增加字段。Collection 采用结果顶层按当前页 ID 索引的 titleCandidates 映射，以保持分页主体轻量。所有结果继续遵守有界读取和响应大小限制。
