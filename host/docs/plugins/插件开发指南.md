# 独立插件开发

先从[公共 API 总览](公共API总览.md)按职责找入口：应用宿主、工作台、仓库核心、文件空间。归属与调用位置分开，外部可用范围以 SDK 白名单及专题契约为准。

插件可在任意明确指定的目录。根目录包含 plugin.json，入口必须在自身目录内；目录名不决定插件 ID。源码可平铺或放 src/，资源在 assets/，业务测试与依赖归本工程。

工作台界面接入先查[结构基线与 API 索引](工作区布局.md#工作台-api-索引)：区分中央页面、普通工具、智能候选和固定实例。容器外观可以调整；插件不要依赖宿主标签栏 DOM 或直接修改本机布局 JSON。

界面的身份与数量先查[内容实例规则](工作区布局.md#内容实例规则2026-11-10)：页面的 `key / instances`、普通工具的稳定 ID、伴随工具的 `context / detachable` 分别声明；允许区域不决定实例数量，移动不等于复制。

## 按场景选择接口

先确定要增加的是数据、界面入口，还是某个界面内部的协作。已有公共语义优先复用；只有出现新的业务贡献种类时，才由业务插件公开扩展点。

| 具体需求 | 首选入口 | 边界 |
| --- | --- | --- |
| 新数据块、用户可定义的模板 | `CorePlugin.blocks`；动态定义使用 `defines` | 数据归仓库，停用插件保留记录；呈现方式不决定数据结构 |
| 停用后清理自己留下的数据 | `CorePlugin.dataLifecycle` 与仓库维护服务 | 停用默认保留；独立记录显式声明，混合／共享数据保守处理；设置 → 数据维护中预览确认。见[插件数据生命周期](插件数据生命周期.md) |
| 小型折叠／展开等本机偏好 | `host.localState`、`usePluginState` | 按插件与作用域归属，支持显式清理；不存正文／密钥／草稿。见[插件本机界面状态](插件本机界面状态.md) |
| 业务写入，或让 MCP 调用业务 | `CorePlugin.commands`；对外声明 `operations` 的 `effect` 并标记 `operation-effects-v1`；业务只读声明 `queries` | UI 与 MCP 复用同一业务实现。简单读取用 `core.get/query/facet`，不必包一层新查询 |
| 工具／导航内部区域接收文件与素材 | `dropQuery` + `content-drop-v1` | 接收规则按内容实例解析；中央、侧栏、小窗不分支；见[内容拖入](公共UI%20API.md#内容实例接收拖入2026-11-15) |
| 按是否挂有模板等数据块筛选 | `source: blocks`、`blockFacetQuery`、`setHasFilters`、`core.kindCounts` | 声明 `block-facets-v1`；批量计数与原子更新，不读取全体素材只为算数量 |
| 新页面、可停靠工具，或一种打开方式 | `tabTypes`、`toolViews`、`opens` | 内容声明身份、区域和上下文需求，宿主安排容器；不读取容器 DOM |
| 测量内容、监听局部事件、安排绘制或显示浮层 | `useUiEffect`、`useUiFrame`、`UiPortal` | 自动跟随显示窗口并清理旧资源；业务会话不重建。见[插件的显示文档](工作区布局.md#插件的显示文档) |
| 同一查询换成表格／看板等排列 | `layouts` 与 `LayoutDef.Options` | 复用集合的查询、选择和操作；列显示、密度等属于页面／保存视图的布局配置 |
| 进入现有筛选、详情、设置或命令面板 | `facets/facetsFor`、`blockSections`、`settingsSections`、`UiPlugin.commands` 等对应贡献 | 宿主已有契约就直接接入；UI 命令不是 MCP 写操作 |
| 给另一个插件的界面增加业务组件或动作 | 提供方 `extensionPoints`，贡献方 `extensions` | 提供方公开类型和校验，决定如何消费；宿主负责装配、依赖、版本与诊断 |
| 跟随某一个页面，读取目录／控制其筛选等 | 页面 `capabilities` 与工具 `context.requires` | 这是具体页面实例的能力与绑定，不把当前页面状态放进静态贡献 `value` |
| 从阅读选区摘录、提问，或共享编辑草稿 | 公共选区通道、现有编辑会话 API | 沿用位置引用和生命周期；不另造共享状态总线，通用非文字编辑仍按实际需求讨论 |

表格与字段是具体例子：表格拥有 `table.tools` v1 的类型、校验和消费；字段贡献结构编辑工具。字段的独立模板编辑器属于字段插件，选列／列序属于表格插件，两者共用仓库中的稳定定义；宿主不再提供表格专用工具入口。见[表格协作契约](表格协作契约.md)。

新协作要写清：公开载荷及版本、提供方的消费规则、`requires/optional` 依赖、缺少提供方时的行为、组件／异步动作失败处理。类型由提供方的公开包提供，不能引用其内部源码；声明类型依赖不等于运行依赖已满足。涉及后台请求用[服务插件 API](服务插件%20API.md)，不要将窗口内的 `extensions` 当作跨进程服务。

只有现有契约确实缺少公共能力时，才给宿主提出具体场景与阻碍；不为了“全部通用化”重写稳定接口。完整入口见[公共 API 总览](公共API总览.md)、[工作区布局](工作区布局.md)和[插件自定义 UI 扩展点](插件自定义UI扩展点.md)。

## 通过 MCP 验收开发构建

**让编码 Agent 从空工程开始。** 在「应用设置 → AI 接入 · MCP → 允许 AI 新建仓库」选择「新仓库由 AI 托管」，勾选「允许 AI 自主开发插件」。源码版使用当前宿主工具链。发行版需要在同一处选一次已安装开发依赖的宿主源码工程。随后创建的托管库各自取得自主开发许可，现有库可在「开发与验收」中单独调整。该许可允许本机执行插件代码。

1. Agent 通过 `create_library` 建库，等待工作台 ready。`list_ecosystem_catalog({libraryId})` 的 `target.permissions.autonomousDevelopment` 给出该库当前权限。
2. 调 `create_development_project({libraryId, pluginId, title, requestId})`。宿主在该库的 `.rm-plugin-projects` 下创建独立工程，返回 `source`、`sourceId` 和 `toolchain`。编码 Agent 通过自己的文件编辑能力修改 `source` 中的 `plugin.json`、`core.ts` 及业务文件。重试用原 requestId，会拿回同一工程并保留已写源码。
3. 用 `prepare_development_build` 构建，用 `get_development_status` 查看错误或 ready 的 availableHash。用最新 session、revision、sourceId 和 hash 调 `apply_development_build`，按 requestId 等到 completed。再用 `describe_library` 发现新能力，调用它并读回数据。下一版可沿用监听，等到新的 hash 再应用。
4. 多个工程共享该库的开发选择。提交 selection 时带上这次获准范围内所有想保留的来源及对应 hash。正式分发沿用插件打包、安装和用包授权。取消创建策略影响以后新建的库，收回现有库许可请在「开发与验收」中取消该库的自主开发勾选；源码和已加载版本仍保留。

**维护手工登记的源码与验收窗口。** 应用设置的「AI 接入 · MCP」提供独立开发验收模式。先在仓库插件设置配置源码目录和工具工程，再为指定 admin 验收库批准源码与可选截图许可。外部 Agent 可通过 MCP 构建、应用快照、调用插件业务、检查加工与画面，并正常关闭／重开读回数据。源码仍由独立插件工程维护，宿主不接收任意 Shell 命令；手工登记的源码逐库批准，窗口截图另行授权。工具参数、回执与失败处理见[服务 API](服务插件%20API.md#开发验收模式与仓库生命周期2026-11-18)，真实流程命令见[开发与验证](../development/开发与验证.md)。

## 工程与依赖

迁出的工程提供 package.json、锁文件、tools.mjs、AGENTS.md 和本机 .rm-dev.json。先 npm ci；工具位置通过 RM_PLUGIN_TOOLCHAIN 或 .rm-dev.json 的 toolchain 指向已安装依赖的宿主。机器路径不提交。npm run configure 生成编辑器使用的 .rm-sdk.json，tsconfig.json 仅继承该本机配置；移动宿主后重新 configure。check／pack／dev 也会刷新该配置。npm run check 检查类型和边界，npm run pack 输出自身 artifacts/<id>.rmplugin，npm run dev 监听到自身 .build-cache。已有业务测试的工程使用自己的测试命令。

只导入 @resource-manager/plugin-api/…；不跨目录引用宿主私有源码或测试夹具。npm 依赖须在 package.json 声明，打包器不再把宿主全部 node_modules 加到搜索路径。React／React DOM 的 UI 实例由宿主共享，Zod 由公共 schema 工具链明确提供；实际用到它们的工程也须声明对应依赖或 peerDependencies。工具链的版本与宿主同步，不是已发布的 npm SDK。

## 安装分享包

在「设置 → 全局应用 → 套件与插件包 → 安装套件或插件包…」可一次选择多个 `.rmplugin`。统一预览名称、版本、作者声明、依赖和校验结果，确认后逐项安装。安装仅保存到本机应用；再到「当前仓库 → 功能与方案 → 启停功能」勾选所需插件，统一应用并重新加载。

- 相同内容的重复包跳过；已安装包不重复安装。不同版本可同时安装，同一个仓库仍只能选择其中一个。
- 同一 ID／版本的不同内容、损坏包、不支持的能力分别显示原因；同批内部版本冲突不会按文件顺序擅自安装其中一个。修正来源后重新选择。
- 一个包失败不撤销其他成功项，也不阻断其他有效包。结果面板保留逐项状态，「重试失败的 N 项」只处理安装失败项。
- 安装使用预览时校验过的字节；预览后改写源文件不会换掉确认内容。取消、换一批、关闭／重载窗口释放预览，应用重启后未完成批次需要重新选择，已经成功安装的包保留。
- 每批至多 50 个文件，单包沿用 16 MB 限制，待安装字节快照合计至多 128 MB。超过限制的项按提示分批处理，不改变 `.rmplugin` 格式。

替换旧版且保持各仓库启停选择时，使用每个已安装包旁的 **更新…**。成功后自动删除所选旧包；失败可接续，套件固定版本和不可访问仓库不会被静默跳过。详见[插件包更新](插件包更新.md)。

## 开发加载

开发模式统一使用源码目录。旧“关联开发包”入口和单包刷新接口已退役；旧记录不再覆盖正式插件，请重新选择对应源码目录并勾选应用。目录构建生成的包仍是内部不可变快照，不是第二种加载入口。退出开发不删除仓库数据或改写正式版本选择。

设置 → 当前仓库 → 插件开发，可添加多个单插件或插件集合目录。集合只扫描直接子目录；同路径去重，重复 ID 报错。新发现项不自动启用；勾选触发构建，成功后统一应用并重载。失败保留最近明确应用的快照。加载、选择和应用以仓库为界，安装包仍按应用安装。

移除来源只停止发现／构建，该来源已应用的快照和数据保留；从列表取消旧项并应用才退出覆盖。移动工程时先移除失效来源、添加新位置，取消旧路径并选择新路径后统一应用；同 ID 继续沿用数据，未确认前不会偷偷替换代码。移除全部目录并退出开发可恢复正式版本选择。

重载会停止播放／会话并重置会话撤销历史；结构接续不会随退出开发自动撤销。正式分享改变内容须提升包版本。数据兼容与 runtime feature 标记独立于源码路径。

## 发行

宿主 packaging/plugins 仅保存发行元信息、旧块 ID 与动态前缀归属，不包含业务源码。宿主默认构建生成空附带包清单。要构建完整组合，先在 .plugin-sources.local.json 配置 ID 到源码目录（或用 RM_PLUGIN_SOURCES 指定文件），运行 npm run plugins:pack，再以 RM_PLUGIN_BUNDLE=artifacts/plugins/catalog.json npm run build 构建。

RM_PLUGIN_SOURCES 中相对路径基于配置文件，不基于调用目录。RM_PLUGIN_BUNDLE 指定已构建包目录的 catalog.json；打包验证每个包的摘要与 ID。机器源码路径不进入发布包。应用安装既有业务插件时，宿主仍保留必要的旧数据归属。

## 验证职责

插件纯业务测试留在插件工程。必须使用 Host 或冻结历史样本的现有用例暂由宿主可选集成套件保留，显式依赖插件来源配置；不能复制私有夹具到插件伪装独立。后续按风险和重复程度继续精简，不用迁目录掩盖覆盖减少。

## 插件之间的 UI 协作

已有选区、页面能力、布局等契约优先复用；业务确实需要新的静态贡献种类时，可声明 `ui-extension-points-v1`，由提供方公开类型与校验，贡献方通过依赖与稳定 ID 接入。宿主处理装配和诊断，不需要为每个新业务改注册表。见[插件自定义 UI 扩展点](插件自定义UI扩展点.md)与两个独立包示例。

## 设置与 UI 命令

设置可以贡献名称、说明和关键词，宿主保留插件来源；使用 `settings-navigation-v1` 后通过 `host.openSettings` 定位，表单可登记离开前检查。独立 UI 命令使用 `ui-commands-v1` 和 `UiPlugin.commands`，宿主聚合现有入口并固定来源选择，不自动注册快捷键或 MCP 操作。少量常用窗口命令可加 `quickAction` 并声明 `quick-actions-v1`，用宿主标准图标加入最左快捷栏；普通工具不会自动加入。完整示例与前端接线见[设置与命令接入](设置与命令接入.md)。

## 工具容器与页面上下文

普通工具使用 `toolViews` 与 `tool-placement-v1`，只声明基本信息和可选 `placement.regions / default`，无需知道容器；宿主补齐默认组，用户已有摆放优先。需要跟随中央页面的工具可声明 `context-tools-v1`，由智能组按页面能力提供候选、按页面类型保存组合。工具操作保持来源页面身份，隐藏时暂停无用查询。支持独立放置时声明 `bound-context-tools-v1` 与 `context.detachable.maxInstances`，可拖出固定来源工具，原智能入口保留。普通／固定工具如需进入中央标签组，在新声明的 `placement.regions` 中加入 `center`；未声明范围的工具仍仅两侧，跨区保持实例和来源绑定。旧侧栏声明及 `showPanel` 已退役，迁移方式、接口、生命周期和最小示例见[工作区布局](工作区布局.md#智能工具与主页面上下文)。

## 多种打开方式

为同一素材提供多个阅读／使用入口，使用带稳定 `id/title` 的 `opens`，并声明 `open-with-v1`。公共 `host.open` 可指定打开器或调起选择窗口，默认偏好由宿主保存，插件不接触本机路径和系统启动。旧无名打开器可渐进命名。接入与系统查看边界见[打开方式](打开方式.md)。

素材列表可直接使用[公共集合、页面输入与角标](公共集合与页面输入.md)，复用查询、选择与布局，同时独立声明页面能否收录和新建。原文件外部编辑使用 `host.editFile`；自定义编辑管理界面使用 `host.fileEditing`，见[公共工作副本](公共工作副本.md)。

浏览布局通过 `UiPlugin.layouts` 接入集合，不必另写查询、选择和菜单。新增尺寸声明、选项默认值和私有状态能力见[浏览布局](浏览布局.md)；仓库默认与保存视图、页面临时状态分别归属。

工作台布局的预设与浏览布局不同：使用 `workbenchPresets` 贡献区域安排；`workbench-content-v1` 允许附带功能入口，并由 `TabType.workbench` 显式定义可捕获／恢复的呈现，或用 `workbenchPresetUis` 替换管理界面；数据和切换仍由宿主服务托管，见[工作台预设 API](工作台预设API.md)。

插件组合是应用宿主的独立公共能力：声明 `plugin-presets-v1` 后通过 `host.pluginPresets` 管理命名组合、预演依赖和应用当前仓库的选择。组合目录跨库复用，开发来源、业务配置与布局不混入，见[插件组合预设](插件组合预设.md)。

### 同一份数据的独立组织插件

标签分组与层级案例采用唯一基础提供方、各自关系数据和业务入口；不要在两个包重复登记同一数据块。动态层级查询与同字段多分面接入见[层级查询与独立标签插件](层级查询与独立标签插件.md)。

## 分发一组能力与方案

多个独立插件可以打成[本地套件](本地插件套件.md)：`.rmsuite` 包含已有 `.rmplugin` 和静态方案，方案可携带工作台安排。无需新增运行插件，也不必往每个业务插件中写安装／重载代码。使用 `npm run suite:pack -- suite.json output.rmsuite`；单插件原有打包与安装方式继续可用。
