# 能力总线实施计划

2026-11-23 确定方向。能力是一种插件贡献，同一个包可以有界面、消费能力并提供计算。仓库会话负责装配，System 定义加工时机和结果归属。个人配置、引擎位置、密钥与模型属于本机。

| 批次 | 交付 | 通过条件 |
| --- | --- | --- |
| 1 装配与探测 | 静态声明、按库装配、版本化输入、能力状态，内置本机 Provider 提供 `media.inspect@1` | 在 Electron 新导入音频和多轨 MKV，元数据、封面正常；缺少 ffprobe 时能收录并能查到具体原因 |
| 2 重计算 | 音频波形和文本字幕抽取；跨库限流、进度、取消、有界返回和临时文件回收 | 长音频得到真实波形，能选轨；双库并发、换版、取消、关库时结果与进程正确收尾 |
| 3 开放外部实现 | 独立 SDK、开发目录、Provider 运行入口、作者命名空间的静态契约、同名冲突检查、选择引擎和管理页 | 固定消费包版本切换两个实现；升级、停用和重载均有确定状态；带 UI 的插件也能同时充当 Provider |
| 4 引擎交付 | 本机程序或服务、按系统与架构分发的运行包、共享模型、远程传输授权 | 用漫画列页和取页跑通干净环境安装与移除；用户选择的本地执行不会自行切换为上传 |
| 5 迁移与发行 | 迁移封面、预览、截帧、播放代理等剩余依赖，以两份预装清单验证标准版和精简版 | 既有库在精简环境仍可打开，补装引擎后恢复加工；分别测量 macOS、Windows 发行物再决定发布组合 |

## 第一批契约

- 清单可选 `capabilities: { version: 1, consumes: ["media.inspect@1"] }`，`provides` 使用相同的版本化 ID 列表。两份列表可以共存。声明随插件包和目录传递，表示意图。第一批只有宿主的 ffprobe 适配器注册了可执行实现。
- 标准名形如 `media.inspect@1`，作者实验名预留 `作者/领域.能力@1`。升主版本表示不兼容变更。同一契约的实现必须能使用同一输入和输出定义验证。
- 加工调用 `ctx.capabilities.run("media.inspect@1", { id, fileSeq })`。宿主从本次加工的 file 块快照定位已接纳版本，将取消与任务绑定；消费者通过 `inspect` 取得状态。能力接口只接受此次授权的素材引用。
- 返回容器名、时长（秒）、码率（bit/s）、标签及有序轨道。轨道序号为容器内索引，可包含编码、像素尺寸、帧率（帧/秒）、旋转（度）、声道数、采样率（Hz）、附图标记和标签；缺失值省略。播放策略、原始数据与派生块的写入仍由消费插件决定。
- 当前仓库的程序位置在开库时解析。重新装配时重新发现。已有同步命令继续只负责短事务；外部服务的信任模型和账户凭据与能力发现分开。

## 验证与进度

第一批已接入音频元数据、音频内嵌封面选轨与视频元数据。缺少引擎时，仓库的插件装配信息与加工状态会给出原因。第二批已接入共享队列和两种 FFmpeg 加工。第三批开放外部 Provider 装配。

真实验收使用独立的 `RM_USER_DATA`、空的 `LIBRARY_PATH` 和 `CAPTURE_DIR`，构建后以 `CAPTURE_FLOW=media-capabilities` 运行 Electron。测试生成 WAV 与一份双音轨 MKV，正常仓库加工后再启动一个无程序搜索目录的隔离核心验证导入。成功标志为本次输出目录中的 `media-capabilities.json`。另有仅安装 ffprobe 的测试，覆盖轨道顺序、语言与加工按功能降级。

第二批验收以同样的环境变量运行 `CAPTURE_FLOW=media-heavy`。测试加载一个声明消费能力的独立开发插件，在两个临时仓库分别导入 200 秒双声道 WAV 和双语文本轨 MKV。它检查静音段、有声段、指定字幕轨与时间码，并在排队时替换原件、回收素材、关闭仓库。输出标志为 `media-heavy.json`。运行中取消原生解码与超额输出另有进程测试。调用示例见[公共后端 API](../plugins/公共后端%20API.md#受控媒体加工)。

第三批已接入独立插件的 `provider` 入口、作者契约和本机引擎选择。消费方和提供方共用静态契约，仓库打开时按启用快照装配，外部实现的包摘要参与派生失效。接口与示例见[提供本机计算引擎](../plugins/公共后端%20API.md#提供本机计算引擎)。

第三批实测先运行 `node tests/electron/provider-prepare.mjs <新的输出目录>`，生成固定消费包、引擎 A 安装包与引擎 B 开发工程。再用该目录作为 `CAPTURE_DIR`、独立的 `RM_USER_DATA` 和空库路径，以 `CAPTURE_FLOW=provider-engines` 运行开发构建。验收从设置页切换 A/B，导入新文件、替换开发快照、停用和恢复后读取同一个素材。成功标志为 `provider-engines.json`。

### 第四批第一步 · 本机程序和图像产物

能力清单 v2 声明本地实现、系统与程序依赖。应用和本库可分别选引擎，单个就绪本地实现可自动采用。插件详情展示提供和消费的能力。加工按 System 记录依赖，按需与后台请求共享有优先级的队列。原生程序经 `ctx.run` 执行，图像通过二进制传输，在加工有效提交时写入派生缓存。开发者接口、限制以及 v1 兼容规则见[公共后端 API](../plugins/公共后端%20API.md#提供本机计算引擎)。

运行 `node tests/electron/provider-prepare.mjs <新目录> native`，用此目录作为 `CAPTURE_DIR`，其余隔离参数同上，运行 `CAPTURE_FLOW=native-engines`。该流程安装两个普通测试插件，导入新 CBZ，核对页目录、超过 4 MiB 的原图字节、原生进程取消、错误码、引擎停用恢复、原件换版撤下旧页及彻底删除后的缓存。成功标志为 `native-engines.json`。已有 `provider-engines` 用例同时验证了应用默认、本库覆盖和恢复跟随应用。

### 第四批第二步 · 随插件交付本机程序

引擎可以把小型 CLI 放进普通 `.hyplugin`，按目标平台和架构声明。安装、摘要校验、仓库启停和卸载沿用现有插件管理流程。选中的包内程序缺失时会报告不可用。安装预览和仓库插件详情列出随包程序和目标。本步骤适用于可独立运行的小型引擎；共享模型和远程传输授权仍各自需要实际消费场景验证。

上述 native 验收在准备阶段用 C 编译器和 libarchive 开发头文件从源码生成一个独立漫画引擎，支持通过 `CC` 和 `HUOYE_TEST_ARCHIVE_INCLUDE` 选择工具链，目标机需要对应的 libarchive 运行库。用例中的包同时承担列页、取页和可取消的长任务。应用执行阶段无需系统中的同名 CLI。安装后验证取页、启用中的卸载保护、停用后移除包文件，再在移除期间导入一份新 CBZ，重装同一包后验证这份素材补出首张图。

### 按需图像读取

打开阅读页时，符合本地文件契约的取图请求在独立的两个名额内执行。每库每次会话最多缓存 128 MiB 和 512 个条目。正在显示的条目保留，已释放的条目可依最近使用顺序淘汰。全部被占用时新请求返回 CAPABILITY_BUSY。系统 PATH 程序按声明名参与加工指纹，变更 CLI 后可按需手动重建。随包引擎继续由包摘要标识。

独立漫画插件 1.2 的 Electron 验收使用 `node tests/electron/prepare-comic-reads.mjs <临时目录> <comic.hyplugin>`，随后按上面的隔离环境运行 `CAPTURE_FLOW=comic-reads`。主窗与独立小窗按 MIME 和摘要核对三种源图，重载后核对旧地址失效、收藏缩略图和原页恢复。成功标志为 `comic-reads.json`。

### 第四批第三步 · 跨库共享的本机运行包

共享 CLI 和动态库可按平台交付为独立的 `.hyruntime`。应用设置提供安装、启停与移除。每个库在打开时取得不可变的程序快照。已安装的包在本机存一份，用于宿主加工和声明相应程序的外部 Provider。打包命令和输入目录见[公共后端 API](../plugins/公共后端%20API.md#多个仓库共用本机运行包)。

Electron 验收将含有 `ffmpeg`、`ffprobe` 的本机运行包放进全新 `CAPTURE_DIR/ffmpeg.hyruntime`，并以独立 `RM_USER_DATA`、空库路径及 `CAPTURE_FLOW=shared-runtimes` 启动开发构建。测试工具依靠本机 FFmpeg 生成带封面的新歌曲，两个受测仓库关闭系统程序搜索。它从设置安装一次、验证两库补算，再停用引擎，逐库重载，检查占用保护与移除后的原件、封面、缩略图。结果为 `shared-runtimes.json`。共享模型和远程传输授权另行规划。

### 第五批第一步 · 标准版与精简版的视频加工

Windows x64 标准版随包提供 FFmpeg，精简版使用独立的打包配置和发行目录。二者共用应用身份、插件清单和仓库格式。宿主根据每个 System 的程序需求判断可用性。新导入素材可等待引擎补装，已生成的代表图、悬停帧和播放代理可继续读取。升级同一程序按稳定的提供方识别加工结果；旧版已写入的运行包指纹会按本机可识别的旧摘要迁移。

Electron 验收在三份新视频上依次验证随包引擎、移除引擎、补装运行包、运行包升级，以及部分程序损坏和同版本修复。先运行 `node tests/electron/prepare-media-editions.mjs <含 runtime.json 与 bin 的本机 FFmpeg 目录> <全新 CAPTURE_DIR>`，再用独立的 `RM_USER_DATA`、空库及 `CAPTURE_FLOW=media-editions` 运行开发构建。结果在 `media-editions.json`。测试用浏览器解码代表图、悬停预览图和转码代理，并核对升级前后的产物摘要、修改时间及块版本。

Windows 实际安装程序的启动、原生依赖和两版分发体积仍需在 Windows x64 上测量。
