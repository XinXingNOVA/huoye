# AI 使用模式与验收

截至 2026-11-18，独立 Agent 已用公开 MCP 将四张新图整理成可直接浏览的双栏素材库。视觉业务是当前覆盖最完整的样本。判断另一种素材、另一款插件能做到哪一步，要看它是否也走过所需的读、写、读回和交付路径。[实测记录](开发与验证.md)

## 从参与方式找到实际能力

最初的 L0–L3 描述用户如何与 AI 配合。后来改用维护者平时的测试流程查缺口，因为只要在正常应用中用公开 MCP 完成操作、读回结果并处理失败，外部 Agent 就有途径完成同一场景。用户预先授信、事后签收、判断分类好坏，分别记录。验收脚本负责造样本、比预期值和重启进程。独立 Agent 的试用额外检验它能否自己找到入口、用好返回值。

例如验收“把五星横图推给我看”，应让客户端发现本库评分和画幅字段，执行筛选，拿到素材 ID，打开目标页，再按该页的渲染版本和身份核对。仅验证核心查询会漏掉权限、会话和画面三处故障。验证“哪些图值得五星”还需要人给出选择样本。

| 参与方式 | 交给 Agent 的工作 | 已走通的范围 | 当前边界 |
| --- | --- | --- | --- |
| L1a 只读参考 | 查材料、读内容、看图 | 查本库 Schema、业务查询、正文和素材卡；新图可按单张或最多 12 张编号拼版读取 | 文本、代表图和派生项取决于本库插件与加工结果。扫描件 OCR、视频逐帧理解需另行验证 |
| L1b 按规则整理 | 按人给的规则逐项加工素材 | 导入或从空间收录，按素材 ID 等待缩略图、色板、画幅，写标签、星级、笔记、组成员和已有模板字段，读回结果 | 权限约束到本库与操作影响类别。限定某个收件箱、某组词表或某张模板仍靠任务约定；例如标签操作可以写入新的标签文本 |
| L0 托管建库与交付 | 用户给目标，Agent 决定组合并交成品 | 零仓库查目录，按允许的方案后台建库，调整获准插件，建分类和模板，保存筛选视图、编排本库双栏、亮窗。独立 Agent 跑通建库到交付；字段和恢复另有 Electron 验证 | 新库权限取自本机创建策略。正式插件按确切包授权，后台建库需要宿主在运行。源文件清单跟踪导入尝试及可独立验收的业务附加块写入，Agent 接手后仍需核对加工、内容和交付质量 |
| L2 同屏与验收 | 人指出“这几张”，整理后回到相应画面签收 | 读活动页、筛选和选区；打开视图、定位并高亮。三种操作可生成带前后值的持久验收单，推送后可人工修正、确认或撤回 | 定位及渲染回执取决于布局接入，内置瀑布流已验。验收单覆盖标签、星级、字段值；关联任务的写入可在重载后先看草稿再补单，普通写入在原会话建单 |
| L3 操作中的单步辅助 | 在阅读器或素材上直接调用一次 AI | 有右键／选区等插件入口，独立 ai-chat 已能把读者选中的文字带入提问 | “选图后一键补标签并可复核”的视觉用例尚待实现、验收 |

同一间库可以上午交给 Agent 自行整理，下午由人框选几项共同复核。L2 读现场需要 read，临时展示需要 organize，改下次打开时的布局需要 admin。自动化描述何时触发任务，定时 Agent 可以复用这些权限；当前宿主未承担持久排程。开发验收则是另一组显式许可，用于验证插件和应用生命周期。

## 权限与入口

设置入口为「应用设置 → AI 接入 · MCP」。先启用应用连接并复制通用配置，再选目标库权限。同一应用凭据用于获准的库，每次调用仍须标明库身份。现有设置适用于接入这份配置的所有客户端。

| 要做的事 | 本机授权 | Agent 查哪里或如何执行 |
| --- | --- | --- |
| 找库、判断可用能力 | 应用接入；已有库默认为 off | `list_libraries` 发现获准库；`list_ecosystem_catalog` 在零库时也可查建库策略、包、套件，带 `libraryId` 时附本库权限 |
| 查材料、看选区、看验收单 | read | 开库后 `describe_library` 查业务声明与受阻原因，`get_library_status` 查是否就绪；`read_preview` 看素材，`get_workbench_session` 看现场，`review_batch(list/get)` 读单。显式 `show_library` 也可亮窗 |
| 改数据、给人看结果 | organize | `execute_operation` 允许声明为 data 的操作；用 `present_workbench` 临时开页或定位。可建单，也可代为确认或撤回；单据记录决定来自应用还是外部 |
| 改结构和持久工作台 | admin | 按本库声明建组、建模板或保存视图；插件组合与工作台布局均先预演后提交。仍需核对插件实际启用情况和包许可 |
| 在新位置建库、让包参与装配 | 应用授权的建库父目录及新库模式；选方案或插件组合需要托管创建策略。包许可可按已安装套件批量授予 | `preview_library_creation` 检查问题；缺包可提交安装请求，由本机授信后安装。建库策略不覆盖已有库授权 |
| 关联空间、变更原件 | 关联已有空间要 admin 加允许的空间；更新和回收原件分别受本库对该空间的 MCP 授权及空间成员权限约束 | 查询目标空间的实际可用动作，素材移入仓库回收站与处置空间原件各走自己的入口。永久清除只在本机应用处理 |
| AI 自己新建并迭代插件 | 托管创建策略的「允许 AI 自主开发插件」，或该库单独授权。工具工程固定，插件源码由编码客户端写入 | `create_development_project` 返回新工程，复用构建、查状态、应用工具，按公开业务入口验证两版结果。[开发指南](../plugins/插件开发指南.md) |
| 测手工授权的插件、截库窗口、关闭或重载库 | 「开发与验收」模式、目标库 admin 和该库验收许可。源码及工具工程由本机选定，截图另行勾选 | 刷新工具列表后才出现开发工具。窗口截图限指定可见内容窗口。关闭模式时仍可在本机检查、撤销逐库许可 |

能力目录中的 `supported` 描述宿主提供的建库及管理接口，`target.permissions` 描述指定库的授权，`describe_library` 描述当前实际可调用的插件操作。运行时还应看本次目标，例如 `get_processing_status(ids,kinds)` 返回所需产出的状态，`get_workbench_session(tabId)` 返回目标页的查询和渲染版本。[服务插件 API](../plugins/服务插件%20API.md)

## 代码归属

| 遇到的问题 | 优先查的代码 |
| --- | --- |
| Agent 找不到入口、工具参数不明 | `src/plugins/mcp/` 的 stdio、tools、application-service 是协议与分发入口，McpSettings、McpManagement、McpDevelopment 是人配置许可的入口 |
| 工具可见但被拒绝、建库或装配失败 | `src/shared/external-access.ts` 定义仓库能力和外部核心方法清单；`src/main/application-access.ts` 按目标和当前授权执法；library-creation、application-management、development-access 负责各自生命周期 |
| 某款插件不能查或改业务数据 | 查实际加载的插件声明和 `src/core/operations.ts`。视觉业务分别在 tags、rating、fields、collection 等插件工程。UI 与 MCP 共享业务命令，数据仍由仓库核心写入 |
| 窗口没定位、撤回结果有误 | 工作台现场在 `src/renderer/src/workbench-session.ts`，持久编排入口在 `src/main/workbench-control.ts`。批次差异和撤回事务在 `src/core/batch-review.ts`，页面在 `src/renderer/src/tabs/batch-review.tsx` |

目前值得保留的集中点是授权、权威写入、撤回时的冲突处理；适合分布在插件的是业务语义。任务草稿和验收单共用块历史与字段定义生成差异。独立的业务附加块可按素材撤回，依赖多项一致性的命令可由插件显式排除通用验收。用 `node tests/electron/visual-ai-check.mjs --review` 验证真实插件包、跨重启补单与单项撤回。

## 下次扩展如何取舍

1. **用清单接手已登记的任务。** `library_task` 保留每个输入的尝试、失败原因和收录身份。带 `taskId` 的标签、星级、字段值写入在提交时保存验收差异，后续 Agent 可先读草稿再补单。复核加工、分类好坏仍需查看当前素材。旧任务和清单外的历史写入沿用原会话边界。[公开接口](../plugins/服务插件%20API.md#跨会话整理任务) · [中断接手实测](开发与验证.md)
2. **按下一次实际错分扩验收。** 例如移动到文件夹后人又改了归属，撤回应尊重最新归属；笔记则要定义文本冲突怎么交给人处理。两者先各跑一个用例，再扩操作范围。
3. **有委派场景再增加权限。** 若需要“只整理收件箱”或“只能送审，由人签收”，应能分别在设置、能力目录和执行时看到并验证这条边界。目前 organize 客户端可以代办决定。若多 Agent 要分开问责，还要有独立客户端身份。
4. **以重复操作决定 L3。** 如果同一个“给选中图片补标签”经常发生，就让视觉插件提供一个操作入口，沿用已有数据命令和验收单。

独立 Agent 四图实测来自用户反馈。会话冲突、三种改动的跨重启撤回、开发授权和生命周期有 macOS Electron 与 SDK stdio 回归。测试使用临时库，允许本机人工入口完成授信和修正，启动和重启由外层脚本控制。Windows、其他媒体组合、分类质量、长时间无人值守分别需要自己的样本与结论。[开发与验证](开发与验证.md) · [原始实施规划](L0全权主理实施规划.md)
