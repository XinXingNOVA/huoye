# 仓库与文件空间

仓库持有素材身份、业务块和明确的文件版本引用；空间持有文件身份、版本字节、成员关系、权限与可用状态。纯文字等原始数据块仍属于仓库，不人为变为文件。

一个仓库可关联多个空间，新库默认建立随库独享空间。独立空间通过成员身份和令牌关联，跨库关联须显式共享；从共享改独享须核对成员记录。随库空间以相对路径绑定，独立空间保存位置并核对仓库身份及位置。

## 操作语义

- 导入：先保存到空间，再按仓库策略收录；发现变化并不意味着立即改变素材。
- 编辑：准备草稿、发布版本、由仓库接纳；另存副本是另一项显式选择。发布与接纳分阶段持久接续。
- 改名：修改仓库显示名；普通业务撤销不回放原件字节。
- 仓库回收／彻底删除：处理素材记录，不隐含删除空间原件。
- 空间回收／恢复：处理原件可用状态，其他库需要发现变化；成功派生结果保留。
- 系统废纸篓：实际处置版本字节；记录归档、明细清理是另外的动作。
- 组合删除：应用先处置原件，再回收本库素材；部分失败保留本库记录，持久任务供明确接续。
- 解除关联与移除本库记录分开；不自动清除仍引用该空间的业务数据。

仓库彻底删除先事务清除身份、相关数据及历史，最外层 `Store.batch`（含调用方生命周期回执）提交后才清理本次产生的缓存候选。嵌套回滚丢弃本层清理任务；提交后重新检查最终引用，外层事务中新增的引用仍受保护。内部 `afterCommit` 只用于可放弃的清理，不对插件开放，也不是持久任务队列；绕过 Store 直接开启的外层 SQL 事务无法确认提交，保守跳过清理。候选只来自已知可重建字段中的 `cache/` 引用并去重；原始字段声明的文件保留。清理一次扫描剩余的原始及派生记录，包括回收站、未知／停用块和嵌套值，仍被引用的缓存不删。扫描无法完成时保守保留候选缓存，缓存清理失败不撤回已完成的记录删除；它不是全库缓存垃圾回收，不读取空间身份或删除空间原件。

MCP 的组织权限、仓库／空间授权与空间成员权限取交集。界面与外部请求的草稿作用域不同，底层业务语义共用。

## 格式与保护

当前格式为 v4；读取引用中的空间／文件／版本身份，不把引用当磁盘相对路径。旧格式明确拒绝；本源码包不包含旧格式迁移工具。当前故障恢复票据、增量补列及相对绑定仍是有效机制。

源码迁移不移动用户仓库。兼容性验证使用完全隔离的副本或新建样本；复制仓库后仍指向真实空间，不算隔离。两个应用不能同时打开同一仓库。不同程序版本交替写入须核验插件定义和存储协议，不仅看文件夹布局。

接口以 src/shared/file-spaces.ts、src/plugin-api/files.ts 和公共文件编辑文档为准。


## 文件读取与回拖定位

主进程的只读空间会话先核对本库关联、空间身份及成员凭据，不构造可写空间、不补表。核心沿用已打开的空间。两条路径共用 `storage/version-read.ts` 的原件状态、版本位置与文件大小／修改时间校验；版本原件的路径组件均不接受符号链接，缓存继续遵循自己的库内路径规则。权限与关联校验仍由各自入口负责，不能把路径解析当作授权。

文件详情在单次调用内复用已完成的读取结果，不使用长期文件状态缓存。缺失、不可用与已回收仍区分，历史内容按指定版本读取，旧格式明确拒绝。

系统回拖按实际登记匹配：输入物理路径 → 所属已关联空间 → 版本记录 → 本仓库当前文件块 → 验证原件可读。只检查命中的素材候选，名称不作为身份；重复输入保持顺序，仓库回收站不参与识别。空间版本路径查询使用现有登记，仓库文件块仍需筛选，没有新建持久索引。旧 `referenceOf()` 和按 `files/<目录名>` 猜身份的 `libraryFileId()` 已退役。


## v4 结构准备与业务调用

`storage/file-space-schema.ts` 集中声明当前结构和已知 v4 增量。新建空间在一次事务内建立完整结构；已有空间由 `FileSpace` 在核对身份、格式与未完成维护状态后准备结构。仅允许补齐已知的权限列、草稿归属列、导入批次、历史恢复、处置与磁盘核对记录表，不重建丢失的原始版本、成员、发布回执等基础表，不提升空间格式版本。

已完整的空间打开时只检查，不取得增量准备的写锁。有待补结构时使用立即事务，获得写锁后重新检查，避免多个仓库同时打开共享空间时重复执行。准备失败整体回滚本次结构修改并关闭连接；现有文件、身份、授权和回执保留。新增权限列默认关闭，早期草稿的调用方默认为 application，不能被仓库借用。

`SpaceVersions`、历史、列表及权限查询依赖已准备的连接，不执行建表或补列。列表在单页内复用版本服务；成员凭据、权限和原件状态仍实时核对，不把它们缓存为永远有效的授权。

主进程的只读空间适配仅验证结构。已知增量尚未准备时报 `FILE_SPACE_SCHEMA_NOT_READY`，应通过应用打开关联仓库或空间后重试；基础表缺失时报 `FILE_SPACE_SCHEMA_INCOMPLETE`，不把不完整数据库重新初始化为空库。结构检查不负责续跑发布或处置任务，既有恢复协议保持独立。


## 刷新与扫描范围

空间通知 `refreshFileSpace(spaceId)`、恢复某个历史版本后的检查，仅扫描目标空间；启动与主动 `scanSpaceImports()` 保持全量。目标范围同时传到本地／外部文件编辑恢复、自动新增收录和版本候选扫描，其他空间的未完成任务留待各自通知或全量检查，不因本次刷新删除或推进。

一轮恢复、收录和版本检查经仓库导入队列执行，开始执行时读取一次 `imports.v1` 策略，避免等待期间的配置被旧快照覆盖。策略读取共用 `core/import-policy.ts`；批量读取的收录关系、版本头与集合只在本次调用内使用，不新增持久索引或长期缓存。实际提交仍通过既有预演、版本及权限校验。

自动收录仍只处理启用后的新身份，每轮最多尝试 100 项，未尝试项优先于失败项；历史收录映射继续阻止回收、撤销及彻底删除后的自动复活。版本扫描既追赶空间事件，也对照本库当前引用，不能因为游标已追平就忽略仓库撤销／引用变化。已发布编辑按回执接纳，无回执的意图不后台发布。

收录空间现有文件不产生复制批次，不再遍历其他空间释放批次令牌。真实导入和失败重试继续清理自己的导入批次，持久回执不删。原件可用性刷新仍保留成功派生数据，只取消不可用任务、重试可用的失败任务。

## 版本接纳与文件块更新

发布编辑后接纳、手动接纳和自动接纳共用 `core/apply-file-version.ts` 更新文件块：保留显示名称及其他原字段，替换版本引用、哈希、大小和格式，清除可重建结果。它只负责这段仓库写入，不负责授权、冲突判断、回执或恢复；调用方先核对可读性和业务基线，在自己的事务内连同映射／候选／回执提交，成功后通知加工。编辑保留准备阶段确定的扩展名，接纳空间版本按该版本文件名确定格式。

自动接纳的请求身份包含本库文件块序号、原引用、目标版本及空间文件修订。相同状态下失败回滚或重开仍可重试；撤销等操作产生新文件块状态后，重新接纳是新意图，不能命中上次成功回执而跳过写入。扫描核对实际引用后才消减待办，回执重放不计为本轮新更新。

显式请求的签名和旧回执保持原规则：同一个请求重试只返回原结果，不因当前引用变化再次执行。开启自动接纳的仓库若撤销操作带回旧引用，下一次扫描仍会按该策略接纳当前版本；需要长期保留旧引用应选择手动接纳。以上不改变 v4 空间或仓库持久化格式。

## 手动磁盘核对与引用接续（2026-11-05）

产品以应用内部的受控文件管理为主，后续优先改善应用发起的修改、版本发布与各仓库同步／接纳体验。绕过应用直接改动原文件只提供手动检查和明确处理选择，作为恢复兜底，不追求对任意外部修改的自动同步。外部编辑器通过应用生成的工作副本参与受控流程：显式检查、确认保存，再由现有版本协议发布和接纳，详见[受控文件编辑](../development/受控文件编辑.md)。系统查看副本继续独立，不自动变为编辑任务。

文件空间的受控版本发布与外部磁盘核对是两个用例。前者知道用户要替换哪一文件；后者对照登记与实际字节，不能靠文件名猜身份，也不能保证被直接覆盖的旧字节仍存在。第一批入口为工作台的「磁盘检查」。核对的是空间内受管文件的登记位置，导入前的外部来源副本没有建立持续跟踪关系。

| 操作 | 处理范围与结果 |
| --- | --- |
| 快速检查 | 检查已登记的当前及历史版本；首次计算 SHA-256，后续复用路径、大小、mtime、ctime、设备与 inode 都未变化的核对结果 |
| 完整检查 | 同一登记范围，重新读取字节计算 SHA-256；用于不信任文件时间／大小的情况 |
| 确认修改 | 用户预览并确认当前版的实际内容后，保存一份经校验的新版本；文件身份不变，旧内容失配记录保留 |
| 重新定位 | 用户明确选择内容相同的文件，校验后复制到受管空间的新位置，更新版本的定位记录；版本 ID、哈希与原引用不变，来源保留 |
| 继续／放弃任务 | 显式重试原请求，或放弃尚未登记的任务；已有发布回执只能完成接续，不能伪装为取消 |

检查不改写原文件、不收录未知路径、不执行自动发布。只保存核对信息；内容哈希相同时可更新已核验的存储时间，不改内容版本身份。清单按版本去重，区分内容改变、缺失、无法读取、写入未稳定；空间或整个文件区不可用会中止检查，不据此批量标记删除。扫描范围取开始时已有的版本上界，分页读取，异步逐文件核对，支持进度与停止；已完成观察保留。列表只代表最近一次观察，不宣称持续监控磁盘。

`SpaceDisk` 管观察、预演与处理；`SpaceVersions` 作为当前 v4 下的有效内容登记适配，仓库 `FileUpdates` 仍独立决定接纳。确认外部修改不伪造用户主动编辑的过程，但需要通过现有版本机制保存有效的新字节。新内容确认仅面向当前、未回收版本；历史版本损坏可重新定位相同内容，不能用任意文件替换历史基线。

确认后：自动接纳仓库沿既有规则更新，手动接纳仓库保留原引用并显示待办；离线仓库重开扫描接续。旧版不可读时，预览仍返回旧版登记及 `unavailable`，允许查看和接纳有效新版。更新文件块、清理派生内容与加工复用现有事务，标签、笔记、名称等用户数据保留；旧版损坏本身无法通过撤销恢复字节。重新定位相同内容恢复所有引用该版本的读取，不生成新版本、不改仓库块、不重新加工成功结果。

底层读取会检查已发现的失配，不能以大小／mtime 恰好相同绕过完整检查结果。观察保存空间内相对位置，不将本机根路径写成新的内容身份。原件物理回收核验成功后清理过期观察，因为 inode 等存储信息已变化。

v4 增量增加三类空间记录：`space_disk_observations` 保存最后观察及后续有效版本，`space_disk_operations` 保存用户确认、登记意图与回执，`space_disk_locations` 登记修复替换下来的旧位置和请求副本。修复仍在原文件的 `files/.versions/<fileId>/` 包内，不覆盖用户改过的旧字节；以后显式物理处置可识别这些位置。若历史字节仍缺失或损坏，现有严格处置／历史恢复规则仍可能阻止操作，应先找回相同内容；本批不增加“忽略损坏并强制删除”。

处理前重新核对来源指纹、空间文件修订和权限；复制后再校验。预览过期、来源持续变化或任务冲突会拒绝提交。修复的定位与回执同事务；新内容登记完成而后续回执失败时，重试依据发布回执接续，不重复生成版本。未登记任务不会在重开时自行发布。主进程按空间串行处理本机检查／确认；存储业务不依赖界面，仓库身份与原有任务协议保持。

磁盘核对不加入后台 watcher、自动启动扫描、未知新文件发现、改名推断或任意外部路径引用；应用发起的工作副本编辑由独立用例处理。复制型重新定位是当前托管布局的修复方式，不等同于以后要探索的引用式管理。

本机工作副本以素材“编辑中”状态呈现，用户完成编辑时由应用层组合发布、接纳与清理；文件空间仍只负责版本与回执，不记录用户窗口的编辑态。详见[受控文件编辑](../development/受控文件编辑.md)。

## 原地目录浏览与身份核对（2026-11-20）

仓库工作台的「文件空间 → 关联或新建空间 → 关联原地目录」可关联现有目录。应用在本机 `userData/file-spaces/<spaceId>/catalog.sqlite` 保存来源根目录及其身份、显式关联的仓库与已观察的目录项。相同来源可供本机多个仓库分别关联。解除前显示当前仓库仍在使用和已在回收站的引用数。解除只撤下本库访问，仍有引用的来源在工作台显示「已解除」，再次选择原目录即可接续。仓库目录改名后，宿主用仓库 ID 与本机记录的目录设备号、文件号及创建时间核实迁移，原位置移走且身份唯一时自动接续。同 ID 副本、跨盘复制和旧登记缺少位置证据时，从工作台重新选择来源。此操作不创建托管 v4 空间。

打开时先列出当前目录，后台逐层补齐首次发现的子目录。「刷新目录」检查当前层，「核对整个空间」也重新走访已浏览过的子目录。离线、无法读取或中途停止时，未完整枚举的目录保留上次成功的清单。目录枚举失败与单文件内容核对失败分别统计。未完成的文件及原因记在本机登记簿，重开仍可查看；「重试未完成项」只重新检查这些文件所在目录，成功后移除失败记录。目录链接及非普通文件跳过。浏览与核对都不会创建仓库素材或复制原件。

每个文件在空间登记簿中有独立 ID。同一位置出现新文件号（包括编辑器的原子保存）时，先查是否有已登记的文件移动至此。若是改名顶替，移动文件接回自己的 ID，被顶替的旧文件列为缺失；若是全新的文件号，沿用原路径的 ID。改名或跨目录移动时，只有能确认原文件已离开旧位置、且设备号、文件号及创建时间唯一匹配的普通单链接文件才能自动接续。独立副本各有自己的 ID。跨卷移动、硬链接或证据不足时，保留旧 ID 及最后路径，可在「原位置缺失」查看。旧版登记簿升级后保留原 ID，首次核对所在目录时补记身份依据。

「核对内容版本」按需分块读取原件并记录 SHA-256，图片预览复用已读字节。首次成功核对为版本 1，此后仅在与上一次成功核对的内容不同时推进版本号。时间戳变化本身不推进版本。登记簿保存最近一次核对结果，不能借此取回历史字节。

### 按类型收录与重新定位

关联原地目录后可以直接浏览，或展开「按文件类型收录」。可选图片、文档、全部文件和自定义后缀；「预览收录」核对整个目录树，再显示匹配数、当前仓库已收录数（含回收站）和待收录样例。确认后核验每个原件，按每 50 个文件一批提交仓库素材，可在仓库侧撤销。扫描排除符号链接、系统杂项文件以及常见工程噪音目录，规则统一在 `directory-policy.ts`。

仓库的文件块保存 `directories/v1/<spaceId>/<fileId>/<sha256>/<name>` 引用。只有在本机仍有明确关联、来源根身份和已核对的文件指纹一致时才能读取原件。空间复核时会重新校验已验证且指纹改变的文件。改名或移动后内容相同，原引用继续有效；若字节发生变化，仓库仍保留其原版本引用、标签和笔记。重复按类型收录不重新创建或复活素材，也不暗中接纳外部改写。在原地空间页打开「本库待接纳更新」，或在素材的文件存储详情中选择「预览更新」，可对照本库摘要、大小和空间当前内容。原地登记簿只记录最近核对结果，外部覆盖后旧字节可能已不可读。确认接纳时重新检查磁盘指纹、空间版本和本库引用，只更新这一库的素材引用并重建派生数据。其他库可以稍后独立决定。原地来源转存托管空间另行处理。

「重新定位根目录」作用于这份空间的全部本机关联。若选中的是原目录本身，按设备号和目录文件号接续。若所选目录身份改变，要求原位置已离线或被替换，至少有一份已核对的文件，并逐一校验当前清单中所有已核对原件的相对路径与 SHA-256。任何一份不符都会中止，不更改旧来源。成功后保留已验证文件的 ID 和仓库引用，未核对的旧文件保留缺失记录，新位置重新登记；未来重新关联、刷新、收录仍然分开。

### 从来源盘点本库素材

在仓库文件空间选中托管空间或原地目录，点「查看本库素材」。清单按仓库实际保留的引用生成，因此解除关联、来源离线或原地登记簿缺失时仍能使用。「主文件」按文件块的当前原件引用归类。「仅附件引用」来自其他原始块声明的文件字段，能读到定义的休眠插件也适用。用途无法判定的引用单列。同一素材在一个来源只计一次，进入回收站后统一在「本库回收站」查看。

主文件可勾选、预览后移入本库回收站或恢复，每批最多 1000 项。确认时重新校验素材身份、主文件来源、回收状态及生命周期预览，任一项变化都要求重新预览。依附批注沿用仓库的回收与恢复规则。附件清单支持打开仓库数据查看。操作只改变当前库的素材状态，来源访问仍由显式关联管理。

「主文件 → 只看核对后缺失」列出本库仍在用、引用版本与空间登记一致、且最后登记位置已确认缺失的素材。原地目录需要先完成「核对整个空间」，让移入其他子目录且可追踪的文件接回原身份。托管空间需要先完成一次「磁盘检查」的快速或完整检查，只采用该轮观察到缺失的当前版本。有新版可接纳的旧引用继续走版本接纳流程。

清单显示最后登记的相对路径。预览和确认都重新核对空间身份、关联和所选文件的位置。原地目录另核对目录树的变动，若预览后找回文件、目录发生变化或检查中断，需要重新核对。每个空间只保存最近一轮的核对凭据。筛选读取目录和文件元数据，无须重新散列原件内容。回收只作用于本库，仍可在「本库回收站」恢复。

### 本机登记簿维护

「应用设置 → 文件空间与外部应用 → 文件空间」可盘点原地目录登记簿的空间身份、来源位置、在线状态、成员仓库、观察文件数、缺失记录数及登记簿文件占用。位置无法确认的仓库允许显式撤下成员；可打开的仓库使用仓库内的解除预览。

缺失记录按上次观察到缺失的时间筛选，预览列出数量和样例。确认时重新核对同一组身份和位置，再一起清理其缺失追踪与过期的内容核对记录。此操作影响所有成员日后自动认回这些文件的能力。源文件、各仓库的素材身份、标签和笔记均保留。SQLite 可复用清理后空出的页，占用不一定马上缩小。

零成员的登记簿持续保留，只有用户确认「忘记本机登记簿」才清理。仓库备份和已解除的库仍可能持有旧引用。执行时核实身份、再次检查成员数并封住并发关联；只移除本机登记目录内认可的 SQLite 文件。中途退出可以在设置页继续清理。
