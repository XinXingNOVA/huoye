# 插件自定义扩展点：设计与成本评估

2026-11-10。已实现窗口内静态 UI 贡献目录、两个独立示例包，以及表格／字段首个业务接入；当前可用 API 以[接入规范](../plugins/插件自定义UI扩展点.md)为准。本页保留设计依据与后续迁移判断，不自动安排全部插件迁移。

## 判断

值得以有限原型验证，成本中等。已有插件装配、依赖筛选、包版本选择、页面上下文和 UI SDK 可以复用；新增部分集中在“插件自己定义贡献契约，宿主收集，提供方使用”。

近期收益是独立插件之间的新协作不必每次扩充宿主的业务接口，方便多 AI 分工与独立发布。它不直接增加用户功能，也不承诺提速。只有一个消费者且没有实际贡献者的功能，继续留在插件内部。

首版限于**当前仓库窗口、启用时静态装配的 UI 贡献**。保持现有统一应用与重载流程；不扩展跨进程服务、MCP、仓库／文件空间格式、运行时热插拔、任意事件总线或通用依赖注入。

## 评估时的实现依据

| 现有机制 | 已实现的协作 | 本次需要辨清的边界 |
| --- | --- | --- |
| `UiPlugin.facets / facetsFor` | 标签、格式与动态模板字段进入同一筛选工具 | 贡献种类仍在宿主声明；业务插件不能自行新增同级注册项 |
| `UiPlugin.layouts` | 集合承载瀑布流、表格、看板，统一查询与选择 | 布局协议是现成公共能力，无需为了通用化立即迁移 |
| `PageContext.capabilities` 与 `toolViews.context.requires` | 主页面可发布自定义能力；其他工具按能力成为候选 | 窗口内实例能力，当前不是任意工具面板均可发布，也不是静态贡献目录 |
| 原 `tableTools`（现已退役） | 模板插件提供表头增列、字段菜单和新增枚举选项；表格消费 | 当时占用宿主专用接口；已迁到插件拥有的 `table.tools` |
| 选区／叠加层 | 阅读器与摘录、批注等插件协作 | 已有公共语义，继续使用，不复制成第二套协议 |
| `requires / optional / needs` | 按仓库启停，整插件依赖与单贡献依赖分开 | 可以复用；依赖存在不代表贡献契约版本兼容 |

可核对：[贡献契约](../../src/plugin-api/ui/contracts.ts)、[页面能力](../../src/plugin-api/ui/page-context.ts)、[页面绑定适配](../../src/renderer/src/page-context.ts)、[UI 装配](../../src/renderer/src/ui-registry.ts)、[表格协作契约](../plugins/表格协作契约.md)、[依赖筛选](../../src/shared/plugin-plan.ts)。评估时表格通过宿主专用 getter 获取字段贡献；当前两者已经使用插件自有契约与通用贡献目录，旧适配整体退役。两者源码仍归独立工程。

## 参考成熟机制

[VS Code 的扩展间 API](https://code.visualstudio.com/api/references/vscode-api#extensions)允许扩展公开 API，由其他扩展声明依赖并取得它；适合直接能力调用。[IntelliJ 的 Extension Points](https://plugins.jetbrains.com/docs/intellij/plugin-extension-points.html)明确允许插件定义自己的扩展点，其他插件提供数据或实现，并要求关注错误归属与动态卸载。

据此作出的项目判断：现有页面能力足够承担首批实例协作；本次缺口更接近后一种“提供方定义契约、其他插件贡献、框架登记”。借鉴其职责，不引入 XML、OSGi、自动激活或完整动态卸载体系。

## 最小职责划分

| 角色 | 负责 | 不负责 |
| --- | --- | --- |
| 扩展点提供方 | 稳定 ID、契约版本、载荷类型与校验、业务上下文、何时调用、如何呈现／选择 | 读取其他插件安装目录、自己维护启用插件总表 |
| 贡献方 | 唯一贡献 ID、目标扩展点与版本、声明依赖、组件或处理函数、自己的业务读写 | 找宿主 DOM、假定当前焦点就是原动作目标、导入提供方内部实现 |
| 宿主 | 所有权检查、两阶段装配、按点建立只读目录、依赖筛选、保留来源与诊断、重载时释放运行环境 | 理解阅读、表格或播放器业务；决定贡献必须画成按钮／Tab |
| 内容实例 | 将本页面／本工具的明确上下文交给选中的贡献，管理实例状态与异步结束 | 把页面状态保存在共享贡献描述符里 |

宿主自带的业务界面可以用 `host.*` 声明同类扩展点，经过同样的贡献装配。宿主注册服务本身是基础设施；内置集合、筛选与外部阅读器的业务贡献可处于同层。没有必要为此把内置功能物理搬成安装包。

这条机制位于内容内部协作层，不改变“区域 → 容器 → 内容”。贡献组件默认只是某个内容里的子组件，不自动获得可停靠、独立状态保存或跨区移动能力；需要独立工具时仍声明 `toolViews`。

## 接口职责

以下是业务接入示意；完整类型、错误边界和可运行示例见接入规范。

```ts
// 阅读器插件：定义自己允许接收的额外动作。
extensionPoints: [{
  id: 'reader.extraActions',
  version: 1,
  validate: validateReaderAction
}]

// 制卡插件：沿用 plugin.json 的 optional: ['reader']。
extensions: [{
  id: 'flashcard.fromSelection',
  point: 'reader.extraActions',
  version: 1,
  needs: ['reader'],
  order: 10,
  value: {
    title: '制作卡片',
    run: createCardFromReadingContext
  }
}]

// 阅读器实例：读取已装配贡献，并在自己的界面安排入口。
const actions = host.extensions.list('reader.extraActions', 1)
// 点击时把本实例的选区、定位与所需方法交给所选贡献；
// 不在注册描述符中捕获一个可变的“全局当前阅读器”。
```

宿主按 `point + version` 返回稳定的只读数组，每项保留 `pluginId / id / point / version / value` 等来源信息。无贡献时返回稳定空数组。目录只登记声明，不提前执行 `run` 或创建 React 实例；同一贡献可以服务多个页面，各页面分别传入上下文。

首版只提供有序列表；按最低优先级唯一胜出、按字段匹配、多项组合等由提供方定义。比如表格可保持“首个匹配生效”的原规则，不把所有贡献都强制渲染出来。也不把图标、标题强加给所有载荷：动作与后台处理器的需求不同。

### 契约与类型归属

- 扩展点 ID 属于提供插件的命名空间，贡献 ID 属于贡献插件；只有宿主能定义 `host.*`。一个 `(point, version)` 只有一个提供者。
- 契约版本使用显式正整数，首版精确匹配；同一提供方可并列提供兼容的旧契约。插件包版本、宿主 `apiVersion`、扩展点版本分别表达发布物、框架协议与协作协议，不能混用。
- TypeScript 类型由提供方公开在纯契约模块／小型类型包中，不能让使用者导入插件入口或组件树。打包器当前拒绝越过插件目录的相对导入，因此不能用 `../../reader/ui` 接入；示例契约可用本地声明依赖，分享时须随源码提供，后续再考虑独立发布。
- 宿主边界接收 `unknown`，提供方执行同步结构校验，返回明确的成功／字段问题结果；校验函数意外抛出异常另按提供方故障处理。类型断言或泛型参数不替代校验。包含函数／组件的 UI 载荷不是 JSON 数据，不入库、不走 IPC、不进入布局存档。
- 不依赖模块对象的引用相等判断契约：不同插件包会独立打包，共享的依据必须是稳定 ID 和版本。

## 装配与生命周期

1. 按现有核心装配结果确定启用插件，加载 UI 模块，检查各包自身声明。模块顶层不得进行贡献注册或启动业务副作用。
2. 在全部 UI 声明收集完之后登记扩展点，再解析贡献的目标与版本。加载先后不能决定协作是否成功。
3. 复用现有 `requires / optional / needs`。跨插件贡献必须声明对提供方的依赖；依赖提供方不反向要求依赖所有贡献方。缺少可选提供方时，该贡献不进入目录，插件其他功能保留。
4. 校验身份、版本与载荷，记录诊断，建立按点索引的稳定快照。贡献级拒绝需要在已有插件管理／加载结果中可查，不能只写控制台；诊断入口属于这批必要成本，不另建调试工作台。同 `order` 使用固定插件／贡献 ID 排序，不能依赖安装时间或异步完成顺序。
5. 业务组件按需读取目录；实例上下文走现有页面能力或明确 props。关闭、失效与异步结果须遵守原业务规则，不因获得贡献就自动拥有状态恢复或编辑会话。
6. 启停、升级继续统一应用并重载，不开放组件挂载时的 `register/unregister`。多个仓库窗口分别装配，不能共用一个进程级当前插件目录。

### 必须处理的失败

| 情况 | 最小行为 |
| --- | --- |
| 可选提供方未安装／停用 | 不激活此贡献；保留其他功能和数据 |
| 必需提供方缺失 | 沿用整插件依赖检查 |
| 提供方在运行，但目标点／版本不匹配 | 拒绝该贡献，明确记录提供方、贡献方与要求版本；不得强行类型转换或悄悄匹配其他点 |
| 重复 ID、冒用命名空间等声明错误 | 归因到声明该项的包，沿用当前包加载失败／恢复策略 |
| 载荷校验返回问题 | 仅拒绝该贡献，诊断归贡献方，其他有效贡献保留 |
| 提供方校验器本身抛出非预期错误 | 归因提供方，拒绝相应装配；校验器错误不能冒充贡献字段错误 |
| 贡献组件渲染或动作执行出错 | 保留贡献来源，分别用组件错误边界与同步／异步调用边界处理；不能仅依赖 React 边界捕获事件与 Promise 错误 |
| 页面关闭或目标数据失效 | 调用方按原实例核验，不改投新活动页；业务写入继续由原命令校验与撤销 |

当前 `external-plugins.tsx` 逐包检查后，按数组顶层 `Component` 包裹组件。自定义贡献的组件可能嵌在 `value.header.Component` 等载荷中，这套包裹不能自动覆盖。首批已提供 `ExtensionBoundary` 与 `host.extensions.invoke`，由提供方明确包装；不能递归代理任意载荷并声称已隔离全部错误。嵌套贡献运行故障只作局部隔离和诊断，不撤下整个包；声明形状错误仍沿用整包恢复。不扩大成沙箱或热卸载系统。

## 实际收益与首个案例

| 场景 | 收益 | 是否需要新增通用目录 |
| --- | --- | --- |
| PDF／EPUB 页面向目录工具公开章节与跳转 | 有用，但现有页面能力可以完成 | 否，优先使用现有机制 |
| 文字选区交给批注、AI 或制卡 | 已有选区协议支撑协作 | 否 |
| 表格接受模板插件的字段菜单、增列与选项编辑 | 现有真实协作，可以把新增表格业务契约从宿主移到插件公开契约 | 是，最适合第二阶段验证 |
| 播放器接受额外的歌曲操作／信息面板 | 后续业务扩展不必改宿主；界面可自由安排 | 有真实第二个贡献插件时再做 |
| 宿主筛选／布局目录改用通用底层 | 统一来源、启停和诊断，减少专用收集代码 | 可以逐步适配，首批无需全迁移 |

表格试点已完成：table／fields 1.2.0 使用 `table.tools`，原匹配、顺序、休眠只读及命令保持。旧入口只在一个声明／读取边界接到同一目录，待用户确认日常库升级后整体退役，见[表格协作契约](../plugins/表格协作契约.md)。

迁移期如保留旧入口，只允许一个注明退役条件的适配层写入同一目录；防止新旧双重登记。需验证旧表格／新模板与新表格／旧模板的组合，不能只检查两个包同时更新。若不值得承担组合成本，可先停留于新示例，不急于迁移已发布业务包。

## 成本评估

以下为源码职责分析，不是已测工时或性能结果。

| 部分 | 成本 | 说明 |
| --- | --- | --- |
| 声明、按点索引与只读读取 | 较低 | 复用现有启用列表；首版无动态订阅、异步注册或状态持久化 |
| 所有权、依赖、版本与载荷校验 | 中等 | 名称相同不等于契约兼容，必须提供确定失败行为 |
| 外部加载与错误归属 | 中等，最需要注意 | 当前逐包验证、顶层组件边界需要适配两阶段解析和嵌套贡献 |
| SDK、包能力标记、类型契约与文档 | 中等 | `UiPlugin`、`UiHost`／公共模块、`scripts/plugins/sdk.ts`、包 `uiFeatures` 与运行时能力检测需一致 |
| 两个独立包集成与窗口隔离验证 | 中等 | 同模块自导自用不足以证明跨包机制有效 |
| 迁移全部既有贡献种类 | 高且暂不值得 | 会扩大兼容组合，短期用户收益有限 |

原型主要涉及公共 UI 契约、一个纯装配模块、UI 加载／注册表、宿主读取门面、SDK／包能力声明，以及示例和集成验证几个位置。现有核心数据、MCP、文件空间和持久格式不需要为此变更。

静态目录可在启动时构建一次，查找按点直接取稳定数组，避免每次渲染遍历全部插件；匹配与排序只针对该点或由提供方按上下文缓存。开销预计主要仍来自贡献组件本身。首批核验稳定列表和独立窗口目录，没有做整机启动性能对照，不据此承诺提速或零成本。

## 建议验证批次与停止条件

**第一批已实现：两个独立示例包。** 一个定义扩展点和页面，一个提供动作／小组件；相同提供方代码在两个页面实例使用，检验目标隔离。可再让宿主声明一个极小测试点，验证内置与外部走同一装配算法；不引入新的用户设置页。

测试按四组行为收敛：

1. 声明归属、版本、重复与非法载荷；可选依赖停用、加载顺序交换、稳定顺序和缺失诊断。
2. 真实独立打包和安装：两个包无内部导入，使用同一公开契约；启停后重载恢复。
3. 多窗口／多页面目标隔离；渲染、同步动作、异步动作失败各自归因；页面关闭后不误操作另一页。
4. 后续表格试点复用现有表格／模板与撤销回归，补新旧包混用的必要断言，不复制全部插件业务测试。

**第二批已完成：表格＋模板局部迁移，保留有明确退役条件的旧包适配。** 以删除一条宿主专用业务通道作为收益证据，而不以新增 API 数量算完成。

**第三批不自动排期。** 只有第二个业务场景表明必要，才调整契约或迁移宿主自带贡献。公开所有现有扩展点、接入核心命令或动态热更新均需新的具体需求。

判断是否继续的标准：第三个独立插件能只改自己的工程加入既有扩展点；提供方换外观不要求贡献者改代码；停用与不兼容有可解释结果；宿主不新增该业务的专用分支。若做完每个贡献还要改宿主，或必须先建立庞大的全局服务／消息系统，则退回缩小方案。
